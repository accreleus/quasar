HTTPS is not optional here. Gamepads, Keyboard Lock and microphone capture all
need a secure context, so an HTTP-only deployment quietly loses three features.

You do not have to obtain a certificate. Quasar generates one on first boot and
keeps it.

## The default: Quasar's own certificate

On first boot the control plane writes a self-signed certificate into its state
directory and reuses it from then on. Nothing to configure, and no re-prompting
after a restart.

The one thing you must get right is which names it claims. On an owned install
they are two seed inputs, read at the first install:

```yaml
      QUASAR_PUBLIC_HOST: "192.0.2.50"
      QUASAR_TLS_HOSTS: "quasar.lan,quasar.vpn.example"
```

List every address anyone will type into a browser. LAN IP, hostname, VPN
address, all of them. Get them right the first time: they can be changed later
with `reconfigure`, but the certificate then has to be re-issued (below). On a legacy Compose install the list is `QUASAR_TLS_HOSTS`
in `deploy/.env`.

<Aside type="caution" title="Without this you get a name error, not a trust prompt">
Left unset, the certificate names `localhost`, the loopback addresses, and
whatever the control plane can see on its own interfaces. That last set is the
trap: it runs in a container, so it sees a Docker bridge address like
`172.18.0.3` and never the host's real LAN address.

Visit `https://192.0.2.50:8443` and you get `ERR_CERT_COMMON_NAME_INVALID`.
Clicking through does not help, because the certificate does not claim that
address at all. There is nothing to trust.
</Aside>

## Trusting it on your devices

Accepting the browser warning works, but you redo it per browser and per device,
and it leaves the padlock struck through. Installing the certificate in your
operating system's trust store fixes it once per machine.

Download it straight from the server:

```bash
curl -k https://<host-ip>:8443/v1/tls/certificate.pem -o quasar.pem
```

That endpoint needs no login, which is deliberate and safe. A server
certificate is public by definition: every TLS handshake hands the same bytes to
every client that connects, before any authentication happens. Anyone who can
reach port 8443 can already read it with `openssl s_client`. The route serves the
leaf only, re-encoded from the parsed certificate rather than read off disk, so
there is no file path that could point at a key. The private key is never
returned by any route.

Add `quasar.pem` to your platform's trust store. On macOS that is Keychain
Access, set to Always Trust. On Windows it is the Trusted Root Certification
Authorities store. On Linux it varies by distribution, usually
`/usr/local/share/ca-certificates` followed by `update-ca-certificates`.

Trusting it only helps if it names the address you actually use.

### Check the fingerprint first

On a LAN you control, clicking through is reasonable. On a network you do not
control it is not, and first contact is when it matters, because that is
when the founding admin account gets claimed.

The control plane logs the fingerprint at startup. Compare it against what your
browser shows:

```bash
docker logs quasar-control-plane 2>&1 | grep fingerprint
```

On a legacy Compose install, use `docker compose -f deploy/docker-compose.yml logs
quasar-control-plane` instead.

## Adding a name later

**On an owned install**, the names are machine inputs of the first machine.
Change them with `reconfigure`, which replaces the control plane with the new
names, then re-issue the certificate, which is generated once and kept:

```bash
docker exec -it quasar-recovery quasar-recovery reconfigure --yes \
  QUASAR_TLS_HOSTS=quasar.lan,quasar.vpn.example,192.0.2.50
docker exec quasar-control-plane rm -f /var/lib/quasar-control/tls/cert.pem /var/lib/quasar-control/tls/key.pem
docker restart quasar-control-plane
```

The new certificate has a new fingerprint. Browsers ask again, and GPU hosts you
added stop connecting until you add them again from **Admin, Fleet, Add host**. A
combined host's own agent is not affected. To avoid that, reach Quasar by a name
the certificate already has, or put a [reverse proxy](/quasar/network/reverse-proxy/)
in front for the new name.

On a legacy Compose install the certificate is generated once and kept for ten
years, so adding a name to `QUASAR_TLS_HOSTS` afterwards does nothing by itself.
Delete the certificate and let it regenerate.

<Steps>

1. Add the name to `QUASAR_TLS_HOSTS` in `deploy/.env`.

2. Delete the existing pair.

   ```bash
   docker compose -f deploy/docker-compose.yml exec quasar-control-plane \
     rm -f /var/lib/quasar-control/tls/cert.pem /var/lib/quasar-control/tls/key.pem
   ```

3. Recreate the container.

   ```bash
   docker compose -f deploy/docker-compose.yml up -d --force-recreate quasar-control-plane
   ```

</Steps>

The new certificate has a new fingerprint, so every browser that accepted the
old one warns again, and every machine you added it to needs the new one.

## Supplying your own certificate

**An owned install takes no certificate of its own in this release.** To serve a
certificate from your own authority, or a public one for a name you own, put a
[reverse proxy](/quasar/network/reverse-proxy/) in front that terminates TLS with
it.

On a legacy Compose install, Quasar will serve it directly. Mount both PEM files
into the container and point at them in `deploy/.env`:

```bash
QUASAR_TLS_CERT=/etc/quasar/tls/cert.pem
QUASAR_TLS_KEY=/etc/quasar/tls/key.pem
```

Set both or neither. One alone is a configuration error and the control plane
refuses to start.

What the certificate needs:

- **Every browser-facing name as a subject alternative name.** LAN IP, hostname,
  VPN address, public name if you have one. Modern browsers ignore the common
  name entirely and read only the SAN list. IP addresses go in as IP SANs, not
  DNS SANs.
- **The full chain in the certificate file**, leaf first, then intermediates. A
  leaf on its own validates in `curl` on your machine and fails in a browser
  somewhere else.
- **An unencrypted private key.** There is nowhere to type a passphrase at boot.
- **Extended key usage including server authentication**, which is the default
  for anything issued as a server certificate.

The node agent and `/health` talk to the control plane over plain HTTP on 8080
and are exempt from the HTTPS redirect, so your certificate only ever has to
satisfy browsers.

## Behind a reverse proxy

If your own proxy terminates TLS and forwards to Quasar, its certificate is the
one browsers see and Quasar's own is irrelevant. Check the allowed origins under
Admin, Settings: a proxy that preserves the public host may work with the
same-origin default, while a host-rewriting proxy or several public names needs
an explicit list. See [Behind a reverse proxy](/quasar/network/reverse-proxy/).

## Turning TLS off

A legacy Compose install can set `QUASAR_TLS=off` in `deploy/.env`: HTTP only, and
you lose gamepads, Escape capture and microphone with it. Only do this when
something in front of Quasar is providing HTTPS. An owned install always serves
HTTPS on its TLS port; a proxy in front simply forwards to the HTTP port instead.

## Settings

On an owned install:

| Seed input | Default | Purpose |
| --- | --- | --- |
| `QUASAR_PUBLIC_HOST` | unset | The name or address the console is reached by. The certificate claims it. |
| `QUASAR_TLS_HOSTS` | unset | More names and IPs the certificate claims, comma-separated. |
| `QUASAR_TLS_PORT` | `8443` | The host port of the HTTPS listener. Browser routes on the HTTP port redirect here. |
| `QUASAR_HTTP_PORT` | `8080` | The host port of the HTTP listener. |

On a legacy Compose install, in `deploy/.env`:

| Setting | Default | Purpose |
| --- | --- | --- |
| `QUASAR_TLS` | `auto` | `auto` generates and keeps a self-signed pair. `off` disables the listener. |
| `QUASAR_TLS_HOSTS` | unset | Names and IPs the generated certificate claims. |
| `QUASAR_TLS_CERT` / `QUASAR_TLS_KEY` | unset | Your own PEM files. Set both. |
| `QUASAR_TLS_ADDR` | `:8443` | The HTTPS listener. |
| `LISTEN_ADDR` | `:8080` | The HTTP listener. |
| `QUASAR_HTTP_REDIRECT` | `auto` | Redirects browser routes from HTTP to HTTPS. |
| `QUASAR_TLS_REDIRECT_PORT` | the TLS port | The external port to redirect to, when it differs. |
