<Aside type="danger" title="Do not expose Quasar directly to the internet">
Quasar has not been security reviewed or hardened for public traffic. Use a VPN.
If you expose it anyway, the risk is yours and it is unsupported.
</Aside>

## Why a proxy is not enough

Login and signaling go to the control plane over HTTPS, and proxy fine. The stream
is WebRTC directly between the browser and the GPU host, so the two must reach
each other by IP. A proxied login page with no route to the GPU host gives you a
login and no stream.

## Use a VPN

WireGuard or Tailscale put the client on the same network as the GPU host, so
Quasar behaves as on a LAN.

- **Add the VPN address to the certificate** (`QUASAR_TLS_HOSTS`). See
  [HTTPS and certificates](/quasar/network/https/).
- **The VPN must carry UDP with low latency.** A relayed Tailscale connection adds
  the relay's latency.

## WebTransport from the internet

<Aside type="caution" title="Experimental, and still not a hardened path">
WebTransport is an opt-in, experimental transport in 0.6. A VPN stays the
recommended way in. This section is the one supported way to reach WebTransport
without a VPN.
</Aside>

**On the same network, WebTransport needs nothing.** The browser connects to the
address the host reports. Everything below is for a browser outside it.

**What you need:** a name that reaches the GPU host's router (here
`stream.example.com`), and the agent's WebTransport port (UDP `4433` unless you set
`QUASAR_WT_PORT`).

**What to do:**

1. **Forward UDP `4433` to the GPU host.** The router sends it to the machine that
   runs the node agent, on the same port. Allow it in the host's firewall too.
2. **Tell Quasar the public address.** Open **Admin ▸ Fleet ▸ Hosts**, the host's
   **WebTransport** card, then:
   - **Public URL:** `https://stream.example.com:4433/wt`
   - **Certificate:** *Port forward (the host's own certificate)*

   Or by the API (`certificate` must be `agent`):

   ```bash
   curl -X PATCH https://<control-plane>/v1/admin/hosts/<host-id>/webtransport \
     -H "Authorization: Bearer <admin-token>" -H "Content-Type: application/json" \
     -d '{"public_url": "https://stream.example.com:4433/wt", "certificate": "agent"}'
   ```

   The agent's own certificate is self-signed, and Quasar gives its hash to the
   browser, so the browser trusts it without a public certificate.

**A reverse proxy in front of WebTransport is not supported in 0.6.** Passing
WebTransport through a proxy such as Caddy needs a proxy feature that has not been
released, and it failed in testing. The card still offers *Reverse proxy with a
public certificate* because the API accepts it; it will not stream today.

**How to check:** launch a session from a browser outside your network. The stats
overlay shows `transport  WebTransport`. If it shows WebRTC, the **WebTransport
fallback** row names the cause. Without this setup the player still works: it waits
about 10 seconds for WebTransport, then falls back to WebRTC. The usual causes are a
UDP port that is not forwarded, a host with no public URL, or a certificate set to
*public*.

## On a LAN

Use an address covered by the certificate, and allow the
[required ports](/quasar/reference/ports/#firewall) between the client and host.

## Signaling through a proxy

If you proxy the control plane, preserve the browser-facing address and configure
allowed origins. The settings differ for current and legacy installs: see
[Behind a reverse proxy](/quasar/network/reverse-proxy/).

## When login works but sessions do not

Check the direct network path first:

1. In **Admin ▸ Sessions**, check whether the session is still starting or is
   running with a black screen.
2. ICE stuck at `checking` in the browser console means no candidate pair worked.
3. Check the selected candidate pair in the browser's WebRTC diagnostics and
   confirm the client can route to the GPU host.
