You might want a proxy for a real certificate on a public name, to put Quasar on
port 443 alongside other services, or to bring it under an existing ingress.

The control plane proxies fine. The media path does not go through the proxy at
all, so read
[Reaching Quasar remotely](/quasar/network/remote-access/) before assuming this
gets you internet play.

## On an owned install

Quasar ships no proxy of its own for an owned install: bring yours. The [quick
start](/quasar/start/quickstart/) writes a Caddy, Traefik, nginx or NGINX Proxy
Manager snippet for your public URL. Point it at the control plane's **HTTP**
port (8080 by default), not 8443.

Three things make it work:

- **The proxy passes the original `Host`** and sends `X-Forwarded-Proto`. The
  signaling address handed to the browser is built from them. An owned install
  takes no `PUBLIC_BASE_URL` in this release, so a proxy that rewrites `Host` to
  its upstream address sends browsers to a listener they cannot reach. Every
  snippet the quick start writes preserves it. Invite links are composed from
  the address the admin browses to.
- **The allowed origins** include the public URL. Opening first-run setup through
  the public address and pressing Continue on Basics saves that exact browser
  origin; manage more under Admin, Settings. An owned install has no environment
  override for them, so the Admin list is the only list.
- **`QUASAR_TRUSTED_PROXIES`**, a seed input, names your proxy's address or
  network, so forwarded client addresses are believed only from it. It is read at
  the first install, like the other inputs.

The seed's `QUASAR_PUBLIC_HOST` still names the certificate on the control
plane's own HTTPS port, which you keep for direct LAN access.

## On a legacy Compose install

A legacy stack can use the hardened Compose overlay, which puts Caddy in front
with ACME certificates, stops the control plane publishing its own ports, and
derives the public URL and origins from `QUASAR_PUBLIC_HOST` in `deploy/.env`:

```bash
docker compose -f deploy/docker-compose.yml \
               -f deploy/docker-compose.hardened.yml up -d
```

With your own proxy instead, the settings below go in `deploy/.env`.

### PUBLIC_BASE_URL

```bash
PUBLIC_BASE_URL=https://quasar.example.com
```

Without this, Quasar builds URLs from what its own listener sees. A proxy that
rewrites `Host` then hands the browser a signaling address it cannot reach.

### Allowed origins

```bash
QUASAR_ALLOWED_ORIGINS=https://quasar.example.com
```

This gates the signaling WebSocket. Leave it unset to use the list saved in
Admin, Settings; set, it is an authoritative override. An explicitly empty value
still pins the environment policy and overrides a list saved in Admin. Unset with
no saved list means same-origin only, which is correct for a direct deployment
and for a proxy that preserves the public host consistently.

Rules for the value, and for the Admin list:

- Comma-separated, exact `scheme://host[:port]` entries.
- No path, no query, no credentials.
- `*` is rejected outright.
- A malformed entry stops the control plane from starting.

### QUASAR_TRUSTED_PROXIES

Only trust forwarded client-address headers from proxies you operate. Set it to
the proxy network or address. With the bundled Caddy stack, use that Compose
project's specific bridge subnet, not the broad Docker private-address range.
Empty is safe: forwarded addresses are ignored and the direct peer is used for
rate limiting and logs.

<Aside type="caution" title="Keep your LAN origins in the list">
Adding a public name and overwriting the list instead of extending it breaks
direct access at `https://<lan-ip>:8443`. List every origin people actually use.
</Aside>

Use Admin's access check from the same browser address before launching a
stream. The launch screen distinguishes an unopened signaling connection from a
failed media connection; its signaling advice points to the public address,
WebSocket proxying and allowed origins.

## Proxy requirements

**WebSocket upgrade.** Both `/v1/signal` and `/agent/ws` are WebSockets. A proxy
that does not forward upgrade headers breaks signaling entirely.

**No aggressive buffering** on those paths.

**A generous read timeout.** These connections are long-lived. A proxy that
closes idle connections after 60 seconds will cut sessions.

**Forwarded protocol headers.** Send `X-Forwarded-Proto` so Quasar can tell it is
being fronted and does not try to redirect a request that already arrived over
HTTPS.

## What not to proxy

Node agents connect to the control plane over `/agent/ws` on plain HTTP, and
`/health` is exempt from the HTTPS redirect so healthchecks work.

If the agents are on the same machine or the same trusted network, point them at
the control plane's direct address instead of through the proxy. Fewer moving
parts in the path that keeps your fleet registered is a good thing.

## Checking it worked

Log in from outside, open the library, launch something. If login works and the
session never starts, the origin setting is the first thing to check, then
whether the client can route directly to the GPU host.
