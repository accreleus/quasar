Quasar can update itself. A **platform release** is a matched set of Quasar's own
images (the control plane, which carries the web app, the node agent, and the
recovery actor that replaces them on each machine) built from one commit and
published together. The seed and Postgres are not part of a release. Admin,
Fleet, Releases is where you see which one you are on, which ones exist, and
which of your machines can take one.

This is Quasar updating Quasar. It has nothing to do with the app catalog's
images, which have their own versions and their own [rollout
page](/quasar/admin/images/).

When a newer release is listed, a banner appears across the admin area —
*Quasar X.Y.Z is available* — with a link here. Dismissing it lasts for the
browser session, not forever.

## Installed

The **Installed** section is what this instance is actually running, as reported
by the components themselves rather than read from a configuration file.

- **Control plane** — its version, its commit, the database schema version it is
  on, and when it was built.
- **Node agents** — how many hosts, and how many have not reported an identity.
- **This machine**, on a Quasar-owned install: the control plane's own machine,
  with its install mode, its recovery actor's version and commit, the seed's
  version, and whether the database is Quasar's own or yours.

{/* TODO(#361, #363): the "This machine" block appears once the control plane's own machine is owned (combined and control-only installs). Check the labels against the built surface. */}

Tagged builds containing the release-version fix report the same release version
for the control plane and agent. Branch/source builds report `dev`; the agent’s
Cargo package version is not the Quasar release version. Older agents may still
show `0.1.0`, so use their commit and build time when identifying those installs.

Per-host detail lives in the host drawer on the [Hosts
tab](/quasar/admin/hosts/#build-identity-in-the-host-drawer).

## Channels

An instance follows one **channel** at a time.

| Channel | What it lists |
| --- | --- |
| `stable` | Tagged releases, with notes and a published release manifest. Prereleases are hidden. The default. |
| `beta` | The same tagged releases and the prereleases among them, such as a release candidate. Applied through exactly the same path as a stable release. |
| `edge` | Whatever was last published from a branch. No version and no notes. |

A prerelease has not been through a release cut. It can carry a migration that
the next prerelease revises, and migrations only go forward, so run `beta` on an
instance you can afford to have ahead of stable. Beta orders its list by version,
not by build date: `0.3.0-rc.1` is below `0.3.0`, whichever was built first.

**Switching back to stable never rolls you back.** No channel offers a build that
orders below the one installed. On `0.3.0-rc.1`, stable lists nothing until
`0.3.0` ships, and says that nothing newer has been detected. That is not a
failure and needs no action.

`edge` follows one branch, named in the **Edge branch** field beside the
selector. That field selects nothing while the channel is stable, and it survives
a switch, so you can set it once.

Switching the channel changes **what is listed, never what is installed**, and it
does not start a check by itself.

An edge build can lag behind a tagged release already installed. When its schema
version is the same but its build time is older, it remains listed as **Older
than installed** and cannot be applied. A higher schema version still takes
precedence. If the installed build has no usable timestamp, Quasar cannot make
that age comparison; the existing schema and identity checks still apply.

## Available, and the notes

Each entry shows its name — the version on stable, a short commit on edge — when
it was built, the commit, and the schema version it carries.

A stable release renders the notes published with it. A release with no notes
links to the changes instead. An edge build publishes no notes by design, so the
entry offers a comparison against the installed build.

Nothing below this control plane's own schema version is ever listed. That is the
[one-way migration rule](/quasar/operations/upgrading/#the-hard-rule) enforced in
the product: a release that would take the database backwards is not an option
you can pick by mistake.

## Check now

Detection runs on a schedule as the `platform.release_detect` job — weekly by
default. **Check now** runs that job immediately, which is the same thing as
Run now on the [Jobs tab](/quasar/admin/jobs/#the-release-detection-job). It
reads the release list, and never applies anything.

The subtitle above the tabs says when the last check ran.

## Targets

The **Targets** table lists the control plane and every host, evaluated against
the newest listed release. A target is **Ready** or **Not ready**, and a not-ready
target says why.

| Why it says | What it means |
| --- | --- |
| Already on the newest release. | Nothing to do. |
| Nothing newer has been detected on this channel. | No release is on offer. |
| This target has not reported what it is running. | An older agent, from before this feature. It cannot be updated from here until it is upgraded once by hand. |
| Built from source on the host — update it with git, not from here. | A source install. The published image is a different build and cannot replace one built on the machine. |
| No updater is installed beside this host's stack. | The host has no `quasar-updater` service, so nothing on it can recreate its own containers. |
| The host's agent is not connected. | An offline host. It is skipped, not failed. |
| Waiting on the control plane: this release carries a newer schema. | An agent is never moved past the control plane. |
| Waiting on the control plane, which moves first. | The same ordering rule, during a fleet update. |
| An update is already in flight on this target. | One at a time per target. |
| A fleet update is already running. | Wait for it, or cancel it. |

A host whose agent is **newer than the control plane** is not a target reason but
a fault: it appears under **Needs attention** as *Agent ahead of the control
plane*. That is only reachable if something was moved backwards by hand.

### The manual recipe

Under the table, each not-ready target gets its own block: what it is on, what it
could be on, and the exact commands for *its* situation. A source install gets
the redeploy command, a host with no updater gets the three lines that add one
followed by the pin-and-recreate recipe, and an offline host gets no commands at
all, because nothing is worth typing until it is back.

Those commands are the same ones on the [Upgrading
page](/quasar/operations/upgrading/), and they contain nothing about your
environment: no addresses, no host names, no home directories. You copy them onto
the machine you are already logged into.

## Apply to one host

A ready host offers **Apply**. What happens, in order:

<Steps>

1. **The host is cordoned.** It stops taking new sessions, exactly as
   [draining](/quasar/admin/hosts/#draining-and-removing) does.

2. **The attempt waits for that host's sessions to end**, showing how many are
   left. The confirmation's checkbox — *Update now — ends N live sessions* —
   skips the wait and names the count, because recreating the agent ends them
   either way. Leave it off and nothing is lost.

3. **The host's recovery actor replaces the agent.** It pulls the release's
   digest, stops the old agent and keeps it, stopped and disabled, then starts
   the new one and waits for it to run and report healthy. On a legacy Compose
   host the updater recreates the agent instead.

   {/* TODO(#362): the recovery actor moves first inside the attempt: it replaces `[recovery-actor?, node-agent]` in that order, and the first failure stops the rest. */}

4. **The new agent registers**, on the release's commit, which is what resolves
   the attempt as succeeded. The old agent cannot report its own success; it is
   the thing being replaced.

5. **The cordon is restored to whatever it was before** — a host you had already
   cordoned stays cordoned, one that was serving goes back to serving, whether
   the apply worked or not.

</Steps>

A failed apply records the digests it would have replaced and shows the reason.
If the new agent never came up, or never became healthy, the previous one is put
back by itself: on an owned host the recovery actor removes the new container and
starts the kept one again, with no pull; on a legacy host the updater restores
the previous digest. The history shows **Reverted automatically** beside the
failed apply, and the failure carries the failed container's last log lines. A
pull that failed changed nothing, and the old agent is still running. If the
automatic restore also fails, both failures are recorded and the failure panel
carries the commands to put the host back by hand.

An update interrupted part-way, by a restart of the recovery actor, the engine or
the machine, is finished by the recovery actor's next start before it does
anything else. Interrupted before the old agent was touched, it ends as failed
with the reason `interrupted` and nothing changed. After that point it carries on
to verification. It is never retried on its own: start a new apply when you are
ready.

## Update Quasar

**Update Quasar** appears when a newer release is listed and nothing else is in
flight. It moves the whole instance in one action, in an order that is not
configurable: **the control plane first, then every eligible host, one at a
time.** There is no hosts-only button, because an agent is never moved past the
control plane.

A run with a control-plane step cordons every host for its whole life, so no new
session starts on a machine it is about to update. A run whose control plane is
already on the release has no such step, so it cordons each host only when it
reaches it, and the rest of the fleet keeps taking sessions. The cordons are
released when the run finishes; a host you had already cordoned stays cordoned.
Whether the run also **waits for sessions to end** before the control-plane step
depends on the release:

- **A release that runs no migration does not wait.** Live sessions stream
  straight through the control-plane restart. The agent holds its running
  sessions while the control plane is away, and the browser keeps the media
  path it already has.
- **A release that carries a migration drains the whole instance first** and
  waits for the session count to reach zero. Every migration Quasar has shipped
  was written assuming no session was live while it ran, so the update does not
  gamble on it. The confirmation's checkbox ends the sessions now instead.

The confirmation tells you which case you are in before you press Update.

TODO(#364): a migrating release takes the pre-update dump first, or needs the external-backup confirmation. */}

The control plane then updates itself through the updater beside it,
and the API and the console go away for roughly twenty seconds. The build that
boots reads back the request written down before the restart and reports the
outcome — the process carrying out its own update cannot survive to report
success. Then each host follows in the fleet list's order, cordoned, drained,
updated and uncordoned exactly as a single Apply is.

The run **stops at the first target that fails** and says which. Targets behind
it are already updated; targets ahead of it were never started.

Hosts that cannot take the release are **skipped, not failed** — offline,
source-built, or without an updater. They are listed with their reason and the
run still finishes as succeeded. "Nothing was eligible" is a legitimate outcome.

**Cancel** stops the run before its next target. It never interrupts one in
flight: a pull or a recreate that has started finishes, because interrupting a
recreate is how a stack ends up with no container at all. The flag is stored, so
a cancel pressed while the control plane is restarting is still honoured.

<Aside type="note" title="A source-built control plane is not offered an update">
The published image is a different build from one compiled on the host, and
swapping one for the other leaves a control plane that starts and cannot write
its own state. The control plane learns its own install mode from the updater
beside it, and refuses the run outright when it is source-built or unknown —
nothing moves before the control plane.
</Aside>

### "Quasar was updated"

An admin tab left open across the control-plane step keeps polling through the
restart and says the control plane is restarting rather than showing an error.
Once the served build differs from the one the page was loaded from, a toast
appears: **Quasar was updated — This page is running the previous build**, with a
Reload button. Take it; the tab is running old JavaScript against a new API.

## Revert a host

A host row offers **Revert** once it has one succeeded update behind it. A revert
is an apply aimed backwards: same drain, same confirmation naming the live
session count, same states, targeting the digests recorded as previous on that
host's last succeeded update.

{/* TODO(#362, #365): on an owned host a revert replaces `[node-agent, recovery-actor]` in that order, and never goes below the control plane's floor. */}

It is not a version picker. The only thing on offer is the build that host was
demonstrably running a moment ago, and the confirmation names that digest. A
revert is itself recorded, so it can be reverted in turn.

<Aside type="danger" title="The control plane is never revertible from here">
The control plane carries database migrations, and rolling it below the schema
version already applied is the crash loop described under [the hard
rule](/quasar/operations/upgrading/#the-hard-rule). Agents carry no migrations,
so they can move back — but never above the control plane's own release.
</Aside>

## Developer apply

The **Developer apply** card applies a set of image digests to one Quasar-owned
host without a published release: a contributor's branch build, from an allowed
registry namespace. It is admin-only and never offered or unattended. See
[Developer apply](/quasar/operations/upgrading/#developer-apply) for its rules.

## Install updates automatically

**Off by default.** Admin, Settings, Platform updates, **Install updates
automatically**. With it on, Quasar applies a detected release without waiting
for you, through exactly the fleet run the **Update Quasar** button starts: the
control plane first, then every eligible host.

- **A release that changes the database is never installed this way.** It is
  still detected, listed and bannered, and it waits for you to press the button.
  Such a release empties the instance before its control-plane step, and ending
  every live session with nobody watching is not something to do on a schedule.
- **There is no separate schedule.** An automatic update happens when release
  detection next runs, so the [detection
  job's](/quasar/admin/jobs/#the-release-detection-job) schedule is the window.
  Move the job and you move the update hour.
- **An automatic update is never forced.** It always waits for each host's own
  sessions to end, because nobody is there to agree to losing them.
- **A failure stops that release, not the feature.** Quasar does not retry a
  release whose automatic run failed. A newer release is still installed, and
  applying the failed one yourself clears the block. A run you cancel is not a
  failure, so it is tried again on the next pass.

The detection job's latest run says what happened: its summary carries
`auto_apply`, either `started` with the run id or the reason it did not start
(`carries_migration`, `no_release`, `not_eligible`, `in_flight`,
`failed_before`). A fleet run started this way is marked on this page.

## Release notifications

The banner only helps someone who is looking. **Notifications**, on this page,
takes a webhook URL and posts one message when detection finds a release this
instance could move to. Slack, Discord and ntfy all accept the body as it is.

1. Paste an incoming-webhook URL into **Webhook URL** and save it.
2. Press **Send test**. A test is sent whether or not notifications are on, and
   it never uses up a real release's notification.
3. Press **Turn notifications on**.

Treat the URL as a credential: on those services, knowing it is what lets you
post. Quasar never logs it. Delivery is `https` only and to public addresses
only, so a receiver on your LAN or on localhost cannot be reached directly; put
a public endpoint such as a tunnel in front of it. Each release is announced
once, a failed delivery is retried on the next few detection passes and then
dropped, and a failing webhook never affects detection or the Releases page.

A receiver you wrote yourself can check a signature: store a secret under
Admin, Settings, Secrets, **Release notification signing secret**, and every
delivery carries an
HMAC-SHA256 signature over its timestamp and body. The header format is in the
repository's `docs/upgrading.md`.

## History and the audit log

**Apply history**, below the targets, is every update this instance has made to
itself, newest first: the target, whether it was an apply or a revert, the
outcome, and the digests it replaced. Those recorded digests are what makes
Revert possible, so they are worth keeping — see [Backup and
restore](/quasar/operations/backup/#the-apply-history-and-what-revert-depends-on).

Every action is also written to the [audit log](/quasar/admin/sessions/), with
the admin who started it: `platform.apply.host`, `platform.apply.run`,
`platform.apply.cancel` and `platform.revert.host`.
