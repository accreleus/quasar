## Reading a host

Each host shows its status, when it last sent a heartbeat, its CPU, its storage,
and a set of readiness checks.

The readiness checks are the useful part, because they report what the agent
**found**, not what the configuration claims. A host can be configured for NVENC
and still have no working encoder.

Checks cover the render node, `/dev/uinput` write access, the managed home root,
media reachability through the host firewall, whether GPU faults are visible, and
on NVIDIA the presence of the EGL and 32-bit GL components that a CUDA-only driver
install leaves out.

`xid_visibility` is the odd one out: it reports whether the agent can read
`/dev/kmsg`, which is where the kernel logs an NVIDIA Xid or an amdgpu fault. The
generator makes this an optional diagnostics choice because some hosts do not
provide that device. When enabled, it passes the device read-only and grants
`SYSLOG`, allowing GPU faults to appear in the session trace. Otherwise, read the
host’s `dmesg` when investigating a GPU fault.

`media_reachability` is read from real sessions. It stays unknown until a browser
on another machine has tried one, passes once such a session connects, and fails
when a remote browser's connection attempt never arrives. The failure names the
scoped firewall rule to add. See [Ports and endpoints](/quasar/reference/ports/#firewall).

Driver provisioning is reported as work in progress, and readiness refreshes
while the agent remains connected. A known AV1 driver restriction leaves the host
usable with its other eligible codecs; see
[AV1 driver compatibility](/quasar/tuning/encoders/#av1-driver-compatibility).

### When a check blocks launches

A host always registers, however many of its checks fail, so the console can say
why. Most checks are advice. A check blocks launches only when it rests on
**evidence**, a host probe that exercised the real path or a definite local
observation such as an unwritable home root, **and** it currently fails. Checks
that only look at configuration (a file exists, a firewall rule parses) never
block, and neither does a warning or an inconclusive probe.

A blocking check names what it keeps out:

| Scope | What it blocks |
| --- | --- |
| Host | Every launch on the host. |
| Homes | Every launch on the host that mounts a managed home. |
| GPU | Every launch that would be placed on that one GPU. The host's other GPUs keep serving. |

The gate only reads a fresh report. A host that has not reported readiness in
the last minute is not blocked by it, because a host that has gone quiet is
already out of placement by being offline, and stale evidence must not strand
the fleet.

When readiness is the **only** reason nothing can take a launch, the player sees
`host_not_ready`: the host needs its administrator's attention. The message never
names the check; that detail is on the host's readiness card. Swapping games in a
running session is not affected, because a swap places nothing.

### Overriding a failing check

If you know better than the evidence, **Launch anyway** on a blocking check lets
the host launch despite that one check. The check stays on the card, marked
overridden, so it is never hidden. An override:

- applies to that check on that host only;
- ends by itself the next time the check passes, so it cannot mask a later
  failure;
- is written to the audit log as a warning, with who set it;
- cannot lift a check the agent enforces itself. Those launches would fail on
  the host anyway, so the console refuses the override.

**Withdraw override** removes it. An override whose check the agent no longer reports is
listed as inert: it excludes nothing, and you can withdraw it.

## Build identity in the host drawer

Expanding a host row shows a **Build** block: what that agent actually is, as it
reported itself.

| Row | What it says |
| --- | --- |
| Commit | The commit the agent was built from. |
| Built | When that build was made. |
| Install | **Owned by Quasar** (the host's services are created and replaced by its recovery actor), **Registry** (published images on a legacy Compose stack) or **Built from source** (images compiled on the machine). A source-built host can be told about a release but never given one. |
| Updater | On an owned host, **Recovery actor** when its recovery actor answered the agent, or **Not answering**, when a release cannot be applied there. On any other host, **None**: it has no recovery actor, so a release cannot be applied there. A legacy Compose host on a release from before owned installs may still read **Present**, for the `quasar-updater` service in its stack. |

Any of these can read **Unknown**, and on an agent from before the self-update
feature they all will: it has no way to say what it is running. Such a host keeps
working exactly as before — it simply cannot be updated from the console until it
is upgraded once by hand, after which it reports its identity like any other. The
Releases tab shows the recipe for it.

### Services on this machine

An owned host's page has a **Services on this machine** card, and the host's
expanded row in the Fleet table shows the same facts. It lists the seed, the
recovery actor and the node agent, each with its version and owner:

- The **seed** is owned by your external manager (Dockge, Arcane or a `docker run`
  line), and Quasar never updates it. It reads *not found* when the recovery actor
  finds no running seed: Quasar keeps running, but a deleted recovery actor could
  then not be re-created, so start the seed again. It reads *unknown* when a seed
  is running but its version could not be read.
- The **recovery actor** and the **node agent** are owned by the recovery actor.

If the recovery actor did not answer the agent, the card says so; sessions are
unaffected. For an offline host it shows the last report, with its time.

On a **combined host** the card also lists the database (*Quasar's own* or *Your
own*) and the control plane. A **control-only** machine runs no agent, so it has no host
row: its services appear under Admin, Fleet, Releases, Installed, as **This
machine**.

Two warnings can appear above the card:

- **No seed found.** Quasar is running normally, but if this machine's recovery
  actor is ever deleted, nothing will re-create it. Start the seed again.
- **Another owner's container is in the way.** A container that looks like a
  Quasar service but was not created by this installation, such as a leftover
  Compose stack. The recovery actor never touches it, and updates to this
  machine are blocked until you remove it, and whatever re-creates it.

A GPU host's card has **Remove host** in its footer (see [Draining and
removing](#draining-and-removing)). A combined host's card says instead that the
machine runs the control plane, so it is not removed from here: it is taken
apart with `uninstall` on the machine (see
[Uninstalling](/quasar/operations/uninstall/)).

A host whose node agent or recovery actor is below the control plane's floor
reads **Must update before it can be managed**. It keeps running, but the console
offers it only the update that lifts it; see [Updating
Quasar](/quasar/admin/releases/).

An agent **newer than the control plane** turns up as *Agent ahead of the control
plane* under Needs attention. Nothing is broken, but it is the wrong way round —
the control plane carries the migrations and always moves first. It is only
reachable if something was rolled back by hand. See [Updating
Quasar](/quasar/admin/releases/).

## GPU capacity and admission

Each GPU shows its encode slots and its VRAM, used and free.

A session is admitted to a GPU when two conditions hold.

**Encode slots.** This is the real reservation, and it is race-safe. A GPU has a
finite number of concurrent encodes it can sustain.

**Free VRAM.** A veto, not a reservation. If the GPU's most recent memory sample
shows less free than `QUASAR_VRAM_MIN_FREE_MB` (1024 MB by default), the GPU is
skipped. Very recent launches the sample has not caught up with are debited from
the figure.

The veto abstains rather than blocking when the telemetry is missing, stale or
structurally implausible. An integrated GPU whose entire memory carve-out sits
below the floor would otherwise reject everything. Unknown telemetry is never
allowed to reduce availability.

Set `QUASAR_VRAM_MIN_FREE_MB=0` to turn the veto off and admit on slots alone.

<Aside type="note" title="Declared per-app VRAM is gone">
Apps used to carry a declared VRAM figure. It was never enforceable, because
there is no VRAM cgroup controller to enforce it with, and in practice it was an
admin-typed guess nothing reconciled. Live telemetry replaced it.
</Aside>

### The three launch refusals

`no_host_available` means nothing online could serve the request, usually because
every host is offline. The web client retries it by itself for 20 seconds, which
covers a host that has just reconnected and not yet reported its capacity. If it
persists past that, look at the hosts, not the launch.

`capacity_exhausted` means hosts are up but currently full. Retrying does help,
once something ends.

`host_not_ready` means a host could have taken the launch, but a failing
readiness check keeps it out. See [When a check blocks
launches](#when-a-check-blocks-launches). It clears when you fix or override the
check, not on a timer.

An explicit codec the player picked that no candidate GPU can encode is refused
with the first two as well, rather than started on a codec they did not ask for.

## Per-host settings

Each host has a Settings page. Every setting there has a **source**:

| Source | Where the value comes from |
| --- | --- |
| Deployment setting | What the agent was started with: its environment and its own device detection. The default for most settings. |
| Automatic choice | Quasar picks from what the host has proven. Offered only for the encoder and render node, and only when exactly one GPU has passed its media probe. |
| Explicit value | A value you type. |

Saving records what you want. It does not prove anything applied: each setting
reports its own state beside it, **Verified on the current connection** once the
agent confirms it, or **Not yet verified** until then.

Settings come in two classes.

**Next-session** settings apply to the next session that starts on the host, once
the agent has verified them. ABR mode, container knobs and most tuning are here.

**Restart** settings (the encoder, the render node and the CUDA device) need the
agent to restart, so saving them never applies them. Under **Restart
configuration**, review the values Quasar will apply and press **Approve idle
apply**. From then on the host takes no new sessions, and the agent restarts
once the sessions already on it have finished and its checks pass. **Approval
never ends a running session.** An approval lasts an hour, and a restart of the
control plane also ends one that has not started: nothing changes, and you
review and approve again.

If the approval sits waiting on preparation while nothing is being prepared,
the usual cause is a Steam template warm-up that failed because the change you
are approving is not applied yet. Turn off **Prepare Steam for faster first
launch** under Admin, Library, Sources, Steam, let the apply finish, then turn it
back on. If the new configuration
fails, the agent puts back its last verified configuration and the card says so.
If the settings change after you reviewed them, the approval is refused and asks
you to review again.

An agent from before host policy shows **upgrade required** on the settings it
cannot take this way; edit those in the panels below until it is updated.

## Render node selection

On a machine with more than one GPU, `QUASAR_RENDER_NODE` picks which one the
compositor and encoder use.

Prefer a `/dev/dri/by-path/` path over `/dev/dri/renderD128`, because the
numbered names can move between reboots. See
[Encoders](/quasar/tuning/encoders/#picking-a-gpu-on-a-multi-gpu-host).

For NVENC on a multi-GPU box, `QUASAR_CUDA_DEVICE` selects the CUDA device index
as well.

Left unset, every GPU that passes its probes takes sessions. Placement picks a
GPU for each session, not just a host, so a two-GPU machine runs sessions on
both. Each GPU also advertises its own codecs: a GPU that cannot encode HEVC or
AV1 is simply not picked for a session that needs one. Setting a render node
takes the other GPUs out of placement.

## Placement across hosts

`QUASAR_PLACEMENT_POLICY` on the control plane:

| Value | Behaviour |
| --- | --- |
| `spread` | Default. Prefers the GPU with the most free encode slots, then the most free VRAM. `least-loaded` is the same policy. |
| `locality` | Prefers the host holding the user's most recently used home for that app, and falls back to `spread` when it is full, cordoned or offline. |

Whatever the policy, a user's **existing home stays where it is**. Once a user has
a home for an app on a host, that app launches there for them, so their saves
are always in the session. While that host is offline or full, the player
cannot launch that app, rather than getting an empty home somewhere else. An app's own
[placement](/quasar/admin/apps/#placement) narrows placement further.

### Releasing a home claim

If a host is gone for good, its users' homes are claimed by a machine that will
not come back, and their launches of those apps cannot be placed. Once you have
forgotten the host, Admin, Fleet, Storage, **Home ownership** lists those claims,
and the row menu's **Release claim** lets that user launch again with a new,
empty home. A claim that still records a home on a host that exists cannot be
released. It asks for a note of what you
checked. It moves and deletes no files: if the machine returns with the same
storage root, the old home is picked up again.

## Draining and removing

Drain stops a host accepting new sessions while letting existing ones finish.
Do this before maintenance.

To take a host out of the fleet, press **Remove host** on its page. It drains
the host, waits for its sessions to end, then has the host's recovery actor
remove the node agent and itself. Forget the host here once the page says it was
removed. Adding the machine back under the same node name keeps its history and
lifts the drain the removal took, but not one you set yourself. The
homes and the host's seed stay on the machine; see
[Uninstalling](/quasar/operations/uninstall/). A host that is not connected is
removed with `uninstall` on the machine instead: the console counts a host as
not connected after about a minute without a heartbeat, even while it reads
*draining*, and refuses the removal then with "nothing was removed".

## The console

Each host has a console page for local-display mode, where the host renders to a
physically attached screen, not to a browser. It needs additional privileges — this
machine's display, sound and monitor control — that the default agent does not have.

On a rootful **owned** host, an admin turns console mode on from that page. Doing so
replaces the node agent: the recovery actor recreates it with those additions, verifies
it came up healthy, and only then does console mode read as on. That replacement ends
the host's live sessions, the same way turning it off does. If the new agent does not
become healthy, the recovery actor puts the previous one back and reports why, and
streaming keeps working as before — the setting never claims access the host does not
have. A rootful engine's socket is already equivalent to root on that machine, so
granting the agent its display and sound is not a new exposure.

Console mode on a **rootless** engine is not available yet; it is coming with later
RH-07 work. A Compose or source install keeps granting console access the way it
always has, with [`deploy/overlays/docker-compose.console.yml`](https://github.com/accreleus/quasar/blob/main/deploy/overlays/docker-compose.console.yml)
— an owned host's recovery actor does not read that overlay.

## Storage

Admin, Fleet, Storage shows the managed home directories across your fleet.

Each host can have its own managed-home root. If you want saves to follow users
between machines it must be real shared storage, not merely the same path on
each host; otherwise use locality placement to keep a user near the host holding
their files. The readiness check reports whether the root is visible and
writable from the agent's namespace.

<Aside type="danger" title="Changing a storage root does not migrate data">
Pointing a host at a different directory makes new launches use that directory.
Existing homes remain at the old path until you move them. To a user, changing
the root without migrating data looks like their saves vanished.
</Aside>
