## Reading a host

Each host shows its status, when it last sent a heartbeat, its CPU, its storage,
and a set of readiness checks.

The readiness checks are the useful part, because they report what the agent
**found**, not what the configuration claims. A host can be configured for NVENC
and still have no working encoder.

Checks cover the render node, `/dev/uinput` write access, the managed home root,
media reachability through the host firewall, whether GPU faults are visible, and
on NVIDIA the presence of the EGL and 32-bit GL components that a CUDA-only driver
install leaves out.

`xid_visibility` is the odd one out: it reports whether the agent can read
`/dev/kmsg`, which is where the kernel logs an NVIDIA Xid or an amdgpu fault. The
generator makes this an optional diagnostics choice because some hosts do not
provide that device. When enabled, it passes the device read-only and grants
`SYSLOG`, allowing GPU faults to appear in the session trace. Otherwise, read the
host’s `dmesg` when investigating a GPU fault.

A `media_reachability` warning names the scoped firewall rule the host is
missing, or the half of the media path an existing rule leaves closed. A
default-deny host whose rules already cover the range passes, quoting them. See
[Ports and endpoints](/quasar/reference/ports/#firewall).

Driver provisioning is reported as work in progress, and readiness refreshes
while the agent remains connected. A known AV1 driver restriction leaves the host
usable with its other eligible codecs; see
[AV1 driver compatibility](/quasar/tuning/encoders/#av1-driver-compatibility).

<Aside type="note" title="Readiness and launch checks">
The agent remains available for administration when a readiness check fails.
Required driver, home, template or runtime mounts that cannot be resolved prevent
an affected app launch. Warnings about optional diagnostics do not block it.
</Aside>

## Build identity in the host drawer

Expanding a host row shows a **Build** block: what that agent actually is, as it
reported itself.

| Row | What it says |
| --- | --- |
| Commit | The commit the agent was built from. |
| Built | When that build was made. |
| Install | **Owned by Quasar** (the host's services are created and replaced by its recovery actor), **Registry** (published images on a legacy Compose stack) or **Built from source** (images compiled on the machine). A source-built host can be told about a release but never given one. |
| Updater | On an owned host, **Recovery actor** when its recovery actor answered the agent, or **Not answering**, when a release cannot be applied there. On any other host, **None**: it has no recovery actor, so a release cannot be applied there. A legacy Compose host on a release from before owned installs may still read **Present**, for the `quasar-updater` service in its stack. |

Any of these can read **Unknown**, and on an agent from before the self-update
feature they all will: it has no way to say what it is running. Such a host keeps
working exactly as before — it simply cannot be updated from the console until it
is upgraded once by hand, after which it reports its identity like any other. The
Releases tab shows the recipe for it.

### Services on this machine

An owned host's page has a **Services on this machine** card, and the host's
expanded row in the Fleet table shows the same facts. It lists the seed, the
recovery actor and the node agent, each with its version and owner:

- The **seed** is owned by your external manager (Dockge, Arcane or a `docker run`
  line), and Quasar never updates it. It reads *not found* when the recovery actor
  finds no running seed: Quasar keeps running, but a deleted recovery actor could
  then not be re-created, so start the seed again. It reads *unknown* when a seed
  is running but its version could not be read.
- The **recovery actor** and the **node agent** are owned by the recovery actor.

If the recovery actor did not answer the agent, the card says so; sessions are
unaffected. For an offline host it shows the last report, with its time.

On a **combined host** the card also lists the database (*Quasar's own* or *Your
own*) and the control plane. A **control-only** machine runs no agent, so it has no host
row: its services appear under Admin, Fleet, Releases, Installed, as **This
machine**.

Two warnings can appear above the card:

- **No seed found.** Quasar is running normally, but if this machine's recovery
  actor is ever deleted, nothing will re-create it. Start the seed again.
- **Another owner's container is in the way.** A container that looks like a
  Quasar service but was not created by this installation, such as a leftover
  Compose stack. The recovery actor never touches it, and updates to this
  machine are blocked until you remove it, and whatever re-creates it.

A GPU host's card has **Remove host** in its footer (see [Draining and
removing](#draining-and-removing)).

A host whose node agent or recovery actor is below the control plane's floor
reads **Must update before it can be managed**. It keeps running, but the console
offers it only the update that lifts it; see [Updating
Quasar](/quasar/admin/releases/).

An agent **newer than the control plane** turns up as *Agent ahead of the control
plane* under Needs attention. Nothing is broken, but it is the wrong way round —
the control plane carries the migrations and always moves first. It is only
reachable if something was rolled back by hand. See [Updating
Quasar](/quasar/admin/releases/).

## GPU capacity and admission

Each GPU shows its encode slots and its VRAM, used and free.

A session is admitted to a GPU when two conditions hold.

**Encode slots.** This is the real reservation, and it is race-safe. A GPU has a
finite number of concurrent encodes it can sustain.

**Free VRAM.** A veto, not a reservation. If the GPU's most recent memory sample
shows less free than `QUASAR_VRAM_MIN_FREE_MB` (1024 MB by default), the GPU is
skipped. Very recent launches the sample has not caught up with are debited from
the figure.

The veto abstains rather than blocking when the telemetry is missing, stale or
structurally implausible. An integrated GPU whose entire memory carve-out sits
below the floor would otherwise reject everything. Unknown telemetry is never
allowed to reduce availability.

Set `QUASAR_VRAM_MIN_FREE_MB=0` to turn the veto off and admit on slots alone.

<Aside type="note" title="Declared per-app VRAM is gone">
Apps used to carry a declared VRAM figure. It was never enforceable, because
there is no VRAM cgroup controller to enforce it with, and in practice it was an
admin-typed guess nothing reconciled. Live telemetry replaced it.
</Aside>

### The two capacity errors

`no_host_available` means nothing in the fleet could ever serve the request.
Usually every host is offline. Retrying does not help.

`capacity_exhausted` means hosts are up but currently full. Retrying does help,
once something ends.

## Per-host settings

Each host has a Settings page that overrides its environment configuration
without editing `.env` and restarting anything by hand. Precedence runs: per-host
override, then agent environment, then catalog default.

Settings come in two classes.

**Live** settings apply to the next session on that host. ABR mode, container
knobs and most tuning are live.

**Restart** settings need the agent to restart, which drops any live sessions on
that host. The encoder, the render node and the CUDA device are in this class.
Quasar tells you before it does it.

## Render node selection

On a machine with more than one GPU, `QUASAR_RENDER_NODE` picks which one the
compositor and encoder use.

Prefer a `/dev/dri/by-path/` path over `/dev/dri/renderD128`, because the
numbered names can move between reboots. See
[Encoders](/quasar/tuning/encoders/#picking-a-gpu-on-a-multi-gpu-host).

For NVENC on a multi-GPU box, `QUASAR_CUDA_DEVICE` selects the CUDA device index
as well.

<Aside type="caution" title="Per-session GPU routing does not exist yet">
Placement chooses a host, and the host's configuration chooses a GPU. You cannot
currently route a specific session to a specific GPU on a multi-GPU host.
</Aside>

## Placement across hosts

`QUASAR_PLACEMENT_POLICY` on the control plane:

| Value | Behaviour |
| --- | --- |
| `spread` | Default. Distributes sessions across hosts. |
| `least-loaded` | Prefers the host with the most free capacity. |
| `locality` | Prefers the host that already holds the user's home directory. |

Use `locality` if home directories are host-local instead of on shared storage.
Otherwise a user's saves are on whichever host happened to run the session.

## Draining and removing

Drain stops a host accepting new sessions while letting existing ones finish.
Do this before maintenance.

To take a host out of the fleet, press **Remove host** on its page. It drains
the host, waits for its sessions to end, then has the host's recovery actor
remove the node agent and itself. Forget the host here once the page says it was
removed. Adding the machine back under the same node name keeps its history and
lifts the drain the removal took, but not one you set yourself. The
homes and the host's seed stay on the machine; see
[Uninstalling](/quasar/operations/uninstall/). A host that is not connected is
removed with `uninstall` on the machine instead: the console counts a host as
not connected after about a minute without a heartbeat, even while it reads
*draining*, and refuses the removal then with "nothing was removed".

## The console

Each host has a console page for local-display mode, where the host renders to a
physically attached screen, not to a browser. It needs additional privileges and
a separate compose overlay, and it is not part of the default deployment. An
owned install has no way to enable it in this release: the recovery actor
creates the agent without those privileges, and there is no input for them.

## Storage

Admin, Fleet, Storage shows the managed home directories across your fleet.

Each host can have its own managed-home root. If you want saves to follow users
between machines it must be real shared storage, not merely the same path on
each host; otherwise use locality placement to keep a user near the host holding
their files. The readiness check reports whether the root is visible and
writable from the agent's namespace.

<Aside type="danger" title="Changing a storage root does not migrate data">
Pointing a host at a different directory makes new launches use that directory.
Existing homes remain at the old path until you move them. To a user, changing
the root without migrating data looks like their saves vanished.
</Aside>
