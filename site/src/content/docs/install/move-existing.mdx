title: Move a Compose install
description: Replace a Compose install with one owned by Quasar, and bring its accounts, library and settings with you.
---

An install started from `deploy/docker-compose.yml` and `deploy/.env` is a
[legacy Compose install](/quasar/install/legacy-compose/). Installs owned by
Quasar are a different shape, and nothing converts one into the other in place.
You move by installing afresh with the seed and loading the old database into
the new install before it first starts.

- **The old install keeps working** on the release it has. It is never offered a
  release that ships owned installs, so nothing updates it out from under you,
  and the console shows no new release rather than an error. You can take your
  time.
- **The database comes with you.** You take a dump of the old database, and the
  new install loads it before its control plane first starts. The control plane
  then upgrades the data as it starts, as any update would. Accounts, the app
  library, profiles and settings come back as they were.
- **Hosts are added again, under their old names.** Every agent is replaced, so
  every host from the old install shows as offline until it is added again. A
  host added under its old node name keeps its history, and its users' homes are
  found again.
- **Homes stay where they are.** Nothing is copied. Give the new install the
  same home root, and each user's saves and installed games are where they were.

## Before you start

- Read [Install Quasar](/quasar/install/install/) once, so the new shape is
  familiar: one container per machine, the seed, and Quasar creates the rest.
- Write down, from **Admin**, **Fleet**, each host's **node name** and the home
  root of every machine. Keep the old `deploy/.env` too.
- The new install must be the same release as the old one, or newer. A dump
  from a newer release than the one you install is refused, with nothing
  changed.
- Plan a window with no one playing. Stopping the old stack ends every session.

## Moving

<Steps>

1. **Stop the old control plane and every agent**, but not the database. On the
   first machine, from its stack directory:

   ```bash
   docker compose -f deploy/docker-compose.yml stop quasar-control-plane quasar-node-agent quasar-updater
   ```

   On each other GPU host, stop its agent stack. The one-line command put it in
   `/opt/quasar-agent`:

   ```bash
   docker compose --project-directory /opt/quasar-agent down
   ```

   With the control plane stopped, nothing writes to the database while you
   dump it.

2. **Take a dump of the old database**, in Postgres's custom format (`-Fc`):

   ```bash
   docker compose -f deploy/docker-compose.yml exec -T quasar-postgres \
     pg_dump -Fc -U quasar quasar > quasar-move.dump
   head -c 5 quasar-move.dump; echo    # prints PGDMP
   ```

   If your `deploy/.env` sets `POSTGRES_USER`, use that user in place of
   `quasar`. A plain-text dump (without `-Fc`) is refused later, so check for
   `PGDMP` now.

3. **Stop the old stack on the first machine**, without `-v`:

   ```bash
   docker compose -f deploy/docker-compose.yml down
   ```

   Leaving off `-v` keeps the old database and volumes, so the old install can
   come back. The old containers must be gone, not merely stopped: a leftover
   Quasar container that the new install did not create is an owner conflict,
   which Quasar refuses to act around, and it would also hold ports 8080 and
   8443.

4. **Install the first machine with the seed, holding it for the restore.**
   Follow [Install the first
   machine](/quasar/install/install/#install-the-first-machine) with three
   differences:

   - add `QUASAR_AWAIT_RESTORE=1` (`-e QUASAR_AWAIT_RESTORE=1` with `docker
     run`, or `QUASAR_AWAIT_RESTORE: "1"` in the stack's `environment`);
   - give it the **same home root** as the old stack's `QUASAR_HOME_ROOT`;
   - on a combined machine, set `QUASAR_NODE_NAME` to the old stack's
     `NODE_NAME`, so its own agent takes over the old host.

   The seed installs Quasar's own Postgres and then waits: the control plane is
   not created, and on a combined machine neither is its agent, so the console
   does not come up yet. `docker logs quasar-recovery` says so, with the command
   for the next step. Use Quasar's own database: the restore does not load into
   a database of your own (`QUASAR_DATABASE_HOST`), which you restore with your
   own tools before the install instead.

5. **Load the dump.** On the same machine, where `quasar-move.dump` is:

   ```bash
   docker exec -i quasar-recovery quasar-recovery restore --dump - < quasar-move.dump
   ```

   The `-i` matters: the dump is read from standard input. Before anything is
   changed the restore checks that the file is a whole custom-format dump of a
   Quasar database, and that it is not from a newer release than this one. Then
   it loads it, creates the control plane, and waits until it reports healthy,
   which includes upgrading the data. It ends by printing what it did.

   If it fails before the control plane was created, nothing is kept: fix what
   it names and run the same command again. You can always run it again after
   an interruption, too.

6. **Sign in with your old admin account.** Accounts, the app library, profiles
   and settings are as they were. Every host shows **Offline**, except a
   combined machine's own, which its agent has already taken back.

7. **Add each GPU host again**, under Admin, Fleet, Add host, as in [Add a
   second GPU host](/quasar/install/second-host/), **with its old node name**
   and the same home root it used before. On a combined machine its own agent
   has already taken its old host back. A host added under its old name keeps
   its history and its homes; one added under a new name is a new host, and the
   old one stays offline until you remove it.

8. **Enter stored credentials again.** Saved credentials, such as the
   SteamGridDB key (Admin, Library, Sources) and the values under Admin,
   Settings, Secrets, were encrypted with the old `QUASAR_SECRET_KEY`, and the
   new install has a key of its own. They show as not readable: enter each one
   again.

9. **Verify** as in [Check your install](/quasar/install/verify/): hosts online
   and a real session that plays. Sign-ins carry over with the database, so
   players who were signed in stay signed in.

</Steps>

Once it is installed, `QUASAR_AWAIT_RESTORE` does nothing more and can be
removed from the seed.

<Aside type="caution" title="Keep the old install until you are sure">
Do not run `docker compose down -v`, delete the old volumes, or remove the old
`deploy/.env` until the new install has run a real session. The move only reads
the old database. To go back, take the new install apart (see
[Uninstalling](/quasar/operations/uninstall/)), then bring the old stack back
with `docker compose -f deploy/docker-compose.yml up -d` from its stack
directory, and each GPU host's with `docker compose --project-directory
/opt/quasar-agent up -d`.
</Aside>

## If the restore says no

- **The dump is newer than this install's control plane**: the old stack ran a
  newer release than the one you installed. Take the new install apart with
  `uninstall --purge` and install that release or a newer one.
- **It is not a custom-format archive**, or **`pg_restore` cannot read it**:
  take the dump again with `-Fc`, and check it is whole (`PGDMP` at the start,
  and the same size as on the old machine).
- **This machine's control plane has already been created**: the install was
  not started with `QUASAR_AWAIT_RESTORE=1`, or it has booted since. A dump is
  loaded only before the first boot. Take the new install apart with
  `docker exec quasar-recovery quasar-recovery uninstall --purge`, remove the
  `quasar-machine` volume, and install again with `QUASAR_AWAIT_RESTORE=1`.
- **The control plane did not report healthy** after the load: its first start
  upgrades the old data, and `docker logs quasar-control-plane` says how far it
  got. To try again from the start, take the new install apart as above.

## What does not come across

- **Stored credentials**: they are entered again (step 8).
- **The old hosts' agents.** Each host is added again (step 7).
- **The old stack's files.** There is no compose file and no `.env` in the new
  install, and most `deploy/.env` settings have no input on it: the [environment
  reference](/quasar/reference/environment/) lists what an owned install takes.
- **Portainer.** It is not a supported manager for the new install. Plain Docker
  Engine, Dockge and Arcane are, and a `docker run` seed on Unraid counts as plain
  Docker.

## Staying on Compose

You do not have to move yet. A legacy install keeps working on its release,
with the commands on [Legacy Compose installs](/quasar/install/legacy-compose/).
It simply stops receiving updates.

Building from source with Compose remains available for contributors. It is not
a supported install. See [Set up a checkout](/quasar/developer/getting-started/).
