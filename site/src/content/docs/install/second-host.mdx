Each host runs one node agent. It reports its GPUs, capacity and readiness to the
control plane and receives sessions from it. The control plane holds no GPU state, so
adding a host is enrolling one more agent.

## Before you start

On the new machine you need:

- Linux with a GPU whose kernel driver is loaded (`ls /dev/dri` shows a `renderD*` node).
- Docker Engine and the Compose v2 plugin. The installer does not install Docker.
- On an NVIDIA host, the NVIDIA Container Toolkit.
- Root, or a user with passwordless `sudo`. The script never prompts for a password; if
  your `sudo` asks for one, open a root shell first (`sudo -i`) and paste the command
  there.
- A route to the control plane's `https://` address. Nothing else needs to be open
  towards the control plane; players reach the host directly for media, which the
  host's readiness check reports on afterwards.

## 1. Mint the command

Open the admin console **over `https://`**, go to **Fleet → Enroll host**, and press
**Mint enrollment string**. The dialog shows a command of this shape:

```bash
curl -fsSL -k --pinnedpubkey 'sha256//<key hash>' https://<control-plane>/enroll-host.sh \
  | QUASAR_ENROLLMENT='qenr1.…' QUASAR_REF=<ref> sh
```

The control plane serves the script itself, so it is the script from the tree the
control plane runs, and `<ref>` — the tag or commit it was built from — selects the
matching agent image. A host you add tomorrow runs what the control plane runs today.

If the control plane serves its own self-signed certificate, the dialog also shows that
certificate's fingerprint. It is the same value the control plane printed as
`fingerprint=` when it started; if the two differ, stop — something between your
browser and the control plane is presenting another certificate. With a real-CA
certificate there is nothing to compare and nothing is pinned.

The string inside the command is single use and expires in an hour. Copy the command
whole; it is meant to be pasted, not typed.

<Aside type="tip" title="About -k, and why the string is an environment variable">
`-k` never appears alone. With the default self-signed certificate the command pairs it
with `--pinnedpubkey`, so `curl` trusts nothing except the control plane's own public
key, whose hash the dialog read from the same certificate it shows the fingerprint of.
Anyone on the path presenting another certificate is refused. With a real-CA
certificate neither flag appears and `curl` verifies normally. The agent then pins the
fingerprint inside the string. A token in a URL would land in proxy logs and browser
history; in an environment variable, on a disposable credential, the only trace is your
shell history, and the token is dead within the hour anyway.
</Aside>

## 2. Run it on the new machine

Paste the command as root, or as a user who can `sudo`. The script prints every step and
stops at the first thing it cannot fix itself.

It checks the host the way the agent's own readiness check will: Docker and Compose,
a render node, `/dev/uinput`, unprivileged user namespaces (on Ubuntu 24.04 and later
that means `kernel.apparmor_restrict_unprivileged_userns`, which the script names with
the exact `sysctl` line), and the NVIDIA Container Toolkit on an NVIDIA host.

It then pins the agent image (`ghcr.io/accreleus/quasar/quasar-node-agent` at the
release, or the local `quasar-node-agent:latest` for a source build), writes
`/opt/quasar-agent/docker-compose.yml` with the node-agent service alone — plus the
NVIDIA overlay when needed — and `/opt/quasar-agent/.env`, mode 0600, which is the only
place the enrollment string lands. It starts the agent with `restart: unless-stopped`
and waits until the agent logs that it is enrolled.

> You should see `enrolled: this host is now '<name>' in Admin → Fleet.` The host
> appears in the Fleet table within a few seconds, online.

Re-running the command on the same machine updates that one agent. It never starts a
second one.

## The updater comes with it

The installer starts two containers, not one: the agent, and `quasar-updater`
beside it. That second one is what lets this host be updated from the admin
console later, because a container cannot recreate itself. It is started first
and deliberately without `depends_on`, so a missing updater image never stops the
agent — the host works, it just cannot be handed a release.

If the host's drawer under Admin, Fleet, Hosts says its updater is **None**, the
script said so at the time: either the image could not be pulled or the service
did not start. Set `QUASAR_UPDATER_IMAGE` in the agent's `.env` and bring the
service up, then restart the agent — it reads updater presence once, at boot. The
[Releases tab](/quasar/admin/releases/) shows the exact commands for that host,
and [Upgrading](/quasar/operations/upgrading/#add-the-updater-to-an-existing-install)
has the longer version.

## When it says no

The last line names the reason.

- **`auth_failed`** — the token was expired, already used, minted for another node
  name, or a host with this name already has a live agent (a name cannot be taken over
  while its agent is connected). Mint a fresh string.
- **`cp-tls-pin-mismatch`** — the certificate the control plane presented is not the one
  the string pins. Mint a fresh string from the control plane's own page, or, after a
  certificate rotation, set `CONTROL_PLANE_FINGERPRINT` in `/opt/quasar-agent/.env`.
- **A preflight** — the fix is printed with it. Apply it and re-run the same command; the
  string is still unused.
- **`still connecting`** — the agent has not reached the control plane yet. Follow its
  log with `docker compose --project-directory /opt/quasar-agent logs -f quasar-node-agent`;
  the usual cause is that the control plane's address in the string is not reachable from
  this machine.

## Manual and air-gapped installs

The dialog keeps the bare enrollment string behind **Show the enrollment string**.
`sh deploy/enroll-host.sh --print-compose` (from any checkout) prints the agent-only
Compose file and `--print-nvidia-overlay` the NVIDIA overlay. Put them in a directory
with a `.env` that sets `QUASAR_ENROLLMENT`, `NODE_NAME`, `QUASAR_HOME_ROOT` and
`QUASAR_AGENT_IMAGE`, and `docker compose up -d`. Every knob the agent reads is in the
[environment reference](/quasar/reference/environment/).

The base `deploy/docker-compose.yml` is not a second-host install: its agent depends on
the local stack. The service the installer prints and the base file's node-agent service
are held identical by a test, so a device or mount added to one reaches the other.

## Storage across hosts

Hosts can use different local storage roots. If you want saves to follow a user between
machines, back those roots with shared storage. Otherwise set the `locality` placement
policy so Quasar prefers the host that already holds that user's home directory.
