<Aside type="caution" title="Not tested, not supported yet">
Multi-host is in the architecture from the beginning. The control plane holds no
GPU state, the scheduler places sessions across hosts, and the admin UI is built
around a fleet rather than one machine. None of that is speculative.

What does not exist yet is a tested way to install the second machine. There is
no agent-only Compose file, no installer, and no verification run behind it. Any
recipe published today would be guesswork.
</Aside>

## What already works

Each host runs one node agent. It reports its GPUs, capacity and readiness to
the control plane, and receives sessions from it. The pieces are in place; the
packaging is not.

**Enrolling a second host is one paste, over TLS.** In the admin console, open
Fleet → Enroll host over `https://` and mint an enrollment string. It carries the
control plane's `wss://` address, the fingerprint of its certificate — shown first
and verbatim so you can compare it against the `fingerprint=` line in the control
plane's startup log before you paste — and a per-host token that is single-use and
expires in an hour. Set it as `QUASAR_ENROLLMENT` in the new host's `deploy/.env`.
The agent pins that certificate for both its websocket and its HTTP polls, so
nothing about the default self-signed certificate needs to change for the agent's
sake. A `ws://` address to another machine is refused unless you explicitly opt in
(`QUASAR_ALLOW_PLAINTEXT_AGENT=1`) — the enrollment token and node secret would
otherwise cross the wire in cleartext. Details and the rotation path are in
`docs/configuration.md` under `QUASAR_ENROLLMENT`.

This was verified end to end on 2026-09-03: a second agent enrolled over `wss://`
against a pinned self-signed certificate, a replayed string was refused, a wrong
fingerprint was refused before any credential left the machine, and re-enrolling a
name whose agent was still connected was refused.

Hosts can use different local storage roots. If you want saves to follow a user
between machines, back those roots with shared storage. Otherwise set the
`locality` placement policy so Quasar prefers the host that already holds that
user's home directory.

## If you want to help

The repository has a multi-agent Compose overlay used for scheduler testing. It
runs several agents on one machine and is not a second-host installer.

If you want to work on real agent-only packaging, start with
[GPU and remote workflows](/quasar/developer/gpu-workflows/). The thing to get
right is the runtime contract the base node-agent service carries: host
networking, GPU and `/dev/uinput` access, the PulseAudio sidecar, the managed-home
root mounted at the same path inside and outside the container, and the enrollment
flow that issues a per-node secret on first contact. Copying five environment
variables across is not enough, which is most of why this is not shipped.
