Work down this list. Each step assumes the ones above it passed.

## 1. The control plane answers

```bash
curl http://localhost:8080/health
```

Expected:

```json
{"status":"ok","db":"ok"}
```

This endpoint is deliberately left on plain HTTP and excluded from the HTTPS
redirect, so it works before certificates are sorted out. `"db":"ok"` means
Postgres is reachable and migrations applied.

## 2. The containers are up

{/* TODO(#361): confirm the combined and control-only lists against the owned recipes. */}

Every container Quasar created on a machine carries its installation label:

```bash
docker ps --filter label=io.quasar.installation
```

| Machine | You want |
| --- | --- |
| Combined host | `quasar-recovery`, `quasar-postgres`, `quasar-control-plane`, `quasar-node-agent` |
| Control-only host | `quasar-recovery`, `quasar-postgres`, `quasar-control-plane` |
| GPU host | `quasar-recovery`, `quasar-node-agent` |

Plus the seed, `quasar-seed`, which is yours rather than Quasar's and so has no
installation label. A database you run yourself means no `quasar-postgres`. All of
them should report healthy. The node agent runs with host networking, and its
image healthcheck reads the local agent health endpoint.

The recovery actor lists the same services, with their images and any container
in the way:

```bash
docker exec quasar-recovery quasar-recovery status
```

In the console, each host's **Services on this machine** card shows the same
inventory with versions.

On a [legacy Compose install](/quasar/install/legacy-compose/) the services are
Compose services instead: `docker compose -f deploy/docker-compose.yml ps` lists
`quasar-postgres`, `quasar-control-plane`, `quasar-node-agent` and
`quasar-updater`.

## 3. The node agent registered

Look at Admin, Fleet, Hosts in the web app. Your machine should be listed with a
recent heartbeat.

From the shell, the agent's own health listener answers on the host:

```bash
curl http://127.0.0.1:9091/health
```

```json
{"status":"ok","sessions":0,"connected":true}
```

`connected: true` is the important field. It means the agent's WebSocket to the
control plane is up. If it is false, the agent is running but cannot reach the
control plane. On a GPU host, check the `QUASAR_ENROLLMENT` string it was
installed with: created in Admin, Fleet, Hosts, Add host, it is single use and
expires after an hour by default, or up to 30 days if you chose longer, so a spent or stale one needs a
fresh command. The recovery
actor hands it to the agent as a file (`QUASAR_ENROLLMENT_FILE`), never as an
environment variable. On a combined host the agent enrolls with a local token its
recovery actor generated, and needs nothing from you. [When it says
no](/quasar/install/second-host/#when-it-says-no) lists what the one-line
command reports.

## 4. The GPU was found, and an encoder with it

Open the host in Admin, Fleet, Hosts. You want to see the GPU listed with a
render node path, and an encoder reported against it.

A GPU that appears with no encoder is the common failure and it is not the same
as no GPU. See
[Install and startup problems](/quasar/troubleshooting/install/).

```bash
ls -l /dev/dri
```

If there is no `renderD128` there is no GPU available to containers at all.

## 5. Virtual input works

```bash
ls -l /dev/uinput
```

The file must exist and the agent must be able to open it for **writing**. A
read-only open succeeds even on a broken setup, which is what makes this easy to
misdiagnose. The agent's readiness check tests for write access and reports the
result on the host detail page.

## 6. A session actually streams

This is the only check that proves the whole path. Launch something from the
library in Chrome and confirm you see moving video and hear audio.

<Aside type="caution" title="A session in the `running` state is not proof">
The server can report a session as running while the browser is failing to
decode a single frame. Look at the picture, not the state.
</Aside>

In the session, open the drawer with **Ctrl+Alt+Shift+Q** and turn on
performance stats. You want a non-zero frame rate that is close to the tier you
launched.

## 7. Certificates cover the address you use

If you reach Quasar at `https://192.0.2.50:8443` then the certificate needs to
name `192.0.2.50`. On a legacy Compose install that comes from
`QUASAR_TLS_HOSTS` in `deploy/.env`, set before the first boot. If you missed it,
or added an address later, see [HTTPS and certificates](/quasar/network/https/).

A quick check of what is being served:

```bash
docker exec quasar-control-plane \
  sh -c 'openssl x509 -in /var/lib/quasar-control/tls/cert.pem -noout -text' \
  | grep -A1 'Subject Alternative Name'
```

On a legacy Compose install, use `docker compose -f deploy/docker-compose.yml exec quasar-control-plane`
in place of `docker exec quasar-control-plane`: Compose prefixes its container
names with the project.
