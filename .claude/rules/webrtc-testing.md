# WebRTC / browser testing gotchas

- **Chrome mDNS ICE candidates resolve IN the node-agent container, not on the host (fixed 2026-07-16).** Modern Chrome sends `.local` mDNS hostnames as ICE candidates instead of real IPs (privacy feature, not disableable via flags in recent versions). libnice resolves these via `getaddrinfo` → NSS — and NSS is **container-local** even under `network_mode: host` (host networking shares the network namespace, NOT `/etc/nsswitch.conf` or the NSS modules), so the historical "install avahi on the host" advice never actually reached the containerized agent (sessions survived via peer-reflexive candidates; a browser offering ONLY `.local` candidates would stall at `Checking`). All node-agent images now bake avahi + nss-mdns (D-Bus off, publishing off — pure resolver, can't name-conflict with a host avahi) with `mdns4_minimal` in nsswitch; the baked entrypoints (vulkan/nv128/agent.prod) and the compose `command:` wrappers (dev/nv) start the daemon. Verified live on hermes with host avahi stopped: the container resolved a live Chrome candidate name, and a real session (harness run with `KEEP_MDNS=1` semantics — mDNS hiding left ON) connected Checking→Completed in 60ms with only `.local` remote candidates in the agent log. No host-side avahi/nss-mdns install is needed anymore. Diagnostic: `docker exec <agent> avahi-daemon --check` + `docker exec <agent> getent hosts <name>.local`.
- **A dead SCTP association is a PEER DISCONNECT, not a session failure — and its signature is only in the gst DEBUG text.** When the browser's peer connection dies mid-session, `sctpenc` posts a *generic* `RESOURCE/WRITE` GError on the encode bus whose message names nothing (`"Could not write to resource."`); only the debug half says `gstsctpenc.c(898): on_sctp_association_state_changed: SCTP association went into error state`. So any classifier must match `err.error()` **and** `err.debug()` concatenated — matching the message alone silently never fires (that hole made the stop-race guard dead code, and three Tower sessions on 2026-07-25 went `failed` with the raw text, two of them during the first real WAN user test). The runner now classifies it (`is_sctp_association_error`, defensive contains-match over `SCTP_ASSOCIATION_SIGNATURES`) and ends the session on the clean teardown path: `stopped` + `state_detail = "peer disconnected: WebRTC data channel closed"`, **no** `error_message`, plus a `transport.peer_disconnected` trace event. Ordered before the Vulkan device-lost check so a peer disconnect can never feed the GPU-global fault detector. The audio `webrtcbin` needs no equivalent arm — its pipeline's bus is never pumped and it carries no DataChannel (hence no `sctpenc`).
- **WebSocket URL must derive from `location.hostname`.** Hardcoding `127.0.0.1` in the client breaks when the page is served from a remote host — the browser connects to its own loopback, not the server. Always use `` `ws://${location.hostname}:PORT` `` as the default, with a `?ws=` override for non-standard setups.
- **`--network host` is Linux-only.** Docker Desktop on Mac/Windows cannot share the host network namespace, so ICE UDP never reaches the browser. All browser WebRTC testing must run on a Linux host or VM with `--network host`.
- **`ondatachannel` readyState race.** When the browser's `ondatachannel` event fires, the channel's `readyState` may already be `"open"` — wiring `ch.onopen` after the fact silently misses the event. Always check `if (ch.readyState === "open") { ... } else { ch.onopen = ...; }` immediately inside the `ondatachannel` handler.
- **Flex video layout.** A `<video>` inside a flex column with `flex:1` must NOT also have `height:100%` — that makes it expand to the full container height and pushes the status bar off-screen. Use `flex:1; min-height:0` only.
- **Reading the T7 overlay off `<video>`.** Decode the overlay by `drawImage(video, …)` into a canvas at the video's **intrinsic** `videoWidth/videoHeight` — that's CSS/`object-fit`-independent, so panel sizing never skews the cell coordinates. Sample on `video.requestVideoFrameCallback` (fires per *displayed* frame) so glass-to-glass is measured to actual presentation, not to a `setInterval` tick. Glass-to-glass needs the ping/pong clock offset (host vs client clock); interactive latency (ping-as-marker) is pure client-clock, so it carries no offset error.
- **Web deploys silently blank the SPA for returning browsers (#131).** Two compounding traps: (a) `web/dist` is a **bind mount** into the control-plane container — a from-scratch rebuild (`rm -rf dist`) swaps the directory *inode*, so the running container serves 404 for `/` until the container is **restarted**; (b) browsers cache `index.html` pointing at the old hashed bundle, and a missing `/assets/<old-hash>.js` **falls back to the SPA HTML with 200** — the module script gets HTML, is MIME-blocked with no console error, and React never mounts (blank page, empty `#root`, API fine). After any web deploy: restart the control-plane container if dist was rebuilt from scratch, and hard-refresh (or cache-bust the URL). Server-side fix (no-cache index.html, real 404 for missing assets) tracked in #131.
- **pnpm ≥ 11 silently skips esbuild's postinstall** (`ERR_PNPM_IGNORED_BUILDS`) so `pnpm build` fails; vite 6 also needs Node ≥ 22. Containerized web builds: `node:22` + **npm** (`npm install && npm run build`) is the known-good combo on both hermes and Tower.
- **Frame-rate / drop numbers from `getVideoPlaybackQuality()` are presentation-side** — an occluded/background window shows "dropped" frames that are display throttling, not network loss. Judge delivery by the agent-side `fps`/`encode_ms` in `session_metrics` (admin drill-down or `GET /v1/admin/sessions/{id}/metrics`), and smoothness by `present_interval_sd_ms` (#108 rule).
- **H.264 High does NOT decode in the browser — on EITHER encoder (not just AMD).** The Phase-0 T8 note framed this as a `vah264enc` quirk, but live AS10-03 validation (2026-06-18, hermes VA **and** Tower NVENC) proved Chrome's WebRTC receiver fails to decode an H.264 **High** stream from **both** `vah264enc` and `nvh264enc` (`h264_decode_failed`), while **constrained-baseline** decodes cleanly on both (47/60 fps 1080p). So the browser transport is effectively constrained-baseline-only regardless of GPU vendor; `main`/`high` are reachable only by a future **native client** (AS10-12), which is why per-session profile negotiation (P1-11) exists. **Anything that sets a browser session's `h264_profile` must clamp to constrained-baseline** — AS10-03's launch-by-profile path does this (the AS10-01 catalog's nominal `high` is negotiated down for browser receivers; `profile_id` still records the rung). Verify a new profile/codec path with a real browser decode (`getVideoPlaybackQuality().totalVideoFrames > 0`), never just session `running`.
