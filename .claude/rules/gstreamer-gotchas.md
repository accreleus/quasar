# GStreamer-rs gotchas (Rust, not gst-launch)

These bit real tickets — gst-launch is more forgiving than the Rust GObject API.

- **Never capture a strong element clone into a closure attached to that same element (pad probe or signal) — it's a GObject ref cycle GLib never collects.** This leaked ~505 MiB VRAM + ~27 MiB RSS per session (2026-07-25): the leaked element pins its closures' Arcs (SessionMetrics) and its cached GstContexts (the session's GstVulkanDevice/CUDA/VA display). Read the element via `pad.parent_element()` inside the callback instead; for element↔Arc cross cycles (encoder pads hold `SessionMetrics`, ABR hooks hold the encoder) break them deterministically at teardown (`SessionMetrics::clear_hooks()` drop guard in `run_blocking`). Regression tests: `session::pipeline::probes::tests`.
- **Elements returned from `request-aux-sender` / `request-post-rtp-aux-sender` signal closures go back as plain handles (`Some(element.to_value())`), with no `g_object_force_floating`:** on the pinned 1.28.8 `webrtcbin` sinks the return only if it is floating at both sites, adds it to a bin and drops the reference the signal gave it, so the bin holds the only one; the flag was needed before 1.28.6 (upstream `23da5cc`) because the post-RTP site took a reference unconditionally and a gstreamer-rs element, already sunk at construction, leaked one per transport (the `identity`, its pads and the abs-capture-time extension), while the `request-aux-sender` site never needed it. Regression test: `takeover_tests::aux_senders`, red on 1.28.4.
- **Any element that outlives the encode pipeline keeps the session's GPU device, however small the element (#564).** A `GstElement` keeps every `GstContext` it was given until it is disposed, and a bin hands its contexts to each child, so one leaked `GstRtpSession` held `gst.vulkan.device` for good. The reference came from `webrtcbin`'s `get-stats` (fixed by the vendored `gstreamer-webrtc-stats-rtpsession-leak.patch`); the agent asks for stats when ICE settles, so only sessions a peer connected to leaked. No GPU is needed to find one: run the takeover harness with the leaks tracer and compare what is alive after a session with a peer and one without. Regression test: `takeover_tests::a_streamed_session_gives_back_the_encode_pipelines_contexts`.
- **A thread that creates a Vulkan instance can crash another thread's `vkGetDeviceProcAddr` (#267).** Vulkan-Loader before 1.4.345 (the image has 1.4.341) resolves `vkGetDeviceQueue2`, and only that name, by walking every instance in the process without the lock instance creation holds, while `vkEnumeratePhysicalDevices` on a new instance frees the record of each driver that has no device. `ash::Device::load` asks for that name, so it must never be used: the compositor fork builds every device table with `vulkan_share::load_device`. New instances appear in every session (the compositor's, and one per Vulkan encoder at NULL→READY, since `vulkanh264enc`/`vulkanh265enc`/`vulkanav1enc` have no `set_context` and never adopt the producer's), so the window is always open. The signature is SIGSEGV in `libvulkan.so.1` under `vkGetDeviceProcAddr` on a valid device, up to about two launches in a hundred. To see who touches the loader in a live agent without restarting it, attach gdb with breakpoints on `vkCreateInstance` and `vkGetDeviceProcAddr` that log and continue.
- **An EGL error in the agent log need not come from the compositor (#570).** smithay's EGL debug callback logs every EGL error in the process, and NVIDIA's Vulkan driver keeps an EGL context of its own on the compositor's per-device EGL display, created when the loader loads the driver and destroyed with the last Vulkan instance in the process. smithay terminates a display when its last handle drops, so the display must outlive the instance: the compositor fork parks a handle on the `GstVulkanInstance` (`GsVulkanBuf::new`). Terminating first gives one `eglDestroyContext: EGL_NOT_INITIALIZED` per session on NVIDIA and nothing on Mesa. The fix depends on teardown order: the display is released with the shared device's instance, and that instance outlives the encoder's own only because the session runner keeps the device's `GstContext` until the pipeline is down. Release that context earlier and the line comes back (a log line, not a crash); #575 tracks a hold that does not depend on the order.
- **Leak triage recipe:** `GST_TRACERS='leaks(filters=GstObject)' GST_DEBUG=GST_TRACER:7 GST_LEAKS_TRACER_SIG=1`, then `docker kill -s USR1 <agent>` dumps `object-alive` lines (name + live ref-count). The vendored `/opt/gst` build has NO coretracers — copy the Fedora one in first: `docker exec <c> cp /usr/lib64/gstreamer-1.0/libgstcoretracers.so /opt/gst/lib64/gstreamer-1.0/` + container restart. Fedora's tracer has no stack-trace support; positional filter syntax (`leaks(GstElement)`) fails on 1.28 — use `filters=`.
- **A plugin's init runs at its first use in the process, not at the registry scan** (the scan runs it in the `gst-plugin-scanner` child). For `vulkan`, `nvcodec` and `va` that init opens the GPU driver stack, so the agent loads its encoders' plugins while it holds no session, and the runner loads its own ahead of its source (`pipeline::preload_encoder_plugins`, #267). It is hardening, not the #267 fix. That crash is a data race inside the Vulkan loader (the image ships 1.4.341; the loader changed this locking in 1.4.345), hit on the compositor's thread: building its device function table looks up `vkGetDeviceQueue2`, and that lookup walks every instance's driver list while the session runner creates the encoder's own Vulkan instance and the loader frees driver records. The `vulkan` plugin's init creates one more instance, so the preload takes one trigger out of the first session and does not prevent the crash. The thread names, stage lines and crash report below are what located it; the fix is in the compositor fork (`vulkan_share::load_device`, the #267 bullet above). In the agent segtrap is off (`session::ensure_gst_init`), so a fault during a plugin load keeps its signal instead of becoming `exit(-1)` blamed on the plugin. A probe child keeps segtrap: its exit code is its verdict, and 255 reads as indeterminate where a signal fails the check.
- **An unnamed `std::thread` keeps its creator's kernel name**, so a crash in one reads as `tokio-rt-worker`. Name every thread a session spawns, in 15 bytes or fewer: the kernel cuts the rest (`quasar-session`, `quasar-app-wait`, ...). The compositor fork names its own thread `wayland-display`.
- **A fatal signal leaves a report on stderr** (`crash_report.rs`): the thread, fault address, ip and sp, 48 stack words, the executable mappings and each file's load base, then raw return addresses. Symbols are offline work against the same image: find the `map` line holding the address, take the lowest `map` line of the same file as its base, then `llvm-symbolizer --obj=<file> 0x<address - base>` (or `addr2line -Cfie`). The module docs say what the handler does and does not promise.
- **The agent writes its environment before its threads exist** (`prepare_environment` in `main.rs`, `session::prepare_gst_env`): `setenv` beside another thread's `getenv` is a use-after-free on a libc that frees the old array (glibc before 2.41). One write does not follow the rule: `nvidia_volume::apply_process_env` runs on a blocking-pool thread at agent start, after the runtime's workers exist, because it needs the adopted driver volume. `tests/process_env_convention.rs` holds the table of every write.
- **Enum-typed element properties** (openh264enc `rate-control`/`complexity`, rtph264pay `aggregate-mode`, videotestsrc `pattern`) MUST be set with `.property_from_str("name", "value")`. `gst-launch` coerces integers; the Rust setter rejects an `i32` and panics at `build()`. (A copy-the-gst-launch-line port will compile and then panic at runtime.)
- `webrtcbin` must be at least `READY` before `create-data-channel` (it is "closed" in `NULL`).
- `create-data-channel` returns a `GstWebRTCDataChannel`, which gstreamer-webrtc 0.23 does not bind as a typed struct — emit untyped (`emit_by_name_with_values`) and upcast the returned `Value` to `glib::Object`.
- ICE may jump `Checking → Completed`, skipping `Connected`. Treat both `Connected` and `Completed` as transport-established.
- `waylanddisplaysrc` produces **1 fps** unless a framerate is requested downstream — it honors whatever caps ask for, but defaults low if nothing does. Always put `framerate=N/1` in the caps after the source (`videotestsrc` defaults to 30, which is why a test-src pipeline hides this). It is also damage/rate-driven, so it emits steady frames at the requested rate even for a static scene (no `videorate` needed).
- **DataChannel init parameters** (ordered, max-retransmits, etc.) are passed as a `gst::Structure` second argument to `create-data-channel`. The default `"input"` DataChannel is now **reliable + ordered** (`ordered:true`, SCTP default retransmission) — the input-jitter investigation (2026-06) validated this against Moonlight's `ENET_PACKET_FLAG_RELIABLE` relative-mouse path; a dropped `mm` sample is costlier to perceived smoothness than the small head-of-line delay. The Phase-0 unreliable+unordered config (`gst::Structure::builder("application/data-channel").field("ordered", false).field("max-retransmits", 0i32).build()`) is retained as an A/B fallback via `QUASAR_INPUT_CHANNEL_MODE=legacy`. The structure name is ignored by webrtcbin; only the fields matter.
- **`on-message-string` vs `on-message-data`**: GstWebRTCDataChannel has two message signals. JSON input events are strings — connect to `on-message-string`. Raw bytes use `on-message-data`.
- **Replying on the DataChannel from its own signal closure (T7 pong).** The channel is an untyped `glib::Object` (not bound as a typed struct), and `glib::Object`'s `WeakRef` is **not `Send`** — capturing it in a `connect(...)` closure fails to compile (`*mut c_void cannot be sent between threads`). The emitter is always the signal's first value, so get the channel from `values[0].get::<glib::Object>()` inside the handler and `emit_by_name::<()>("send-string", &[&json])` on it — no capture needed.
- **Writing into a frame in a pad probe (T7 overlay).** `PadProbeInfo::buffer()` is read-only; `buffer_mut()` returns `&mut gst::Buffer` (owned), not a `BufferRef` — call `.make_mut()` on it to get the `&mut gst::BufferRef` that `VideoFrameRef::from_buffer_ref_writable(buffer, &VideoInfo)` needs (it copies iff the buffer is shared, which it isn't for a freshly converted I420 frame). The frame accessors (`width`/`height`/`plane_stride`/`plane_data_mut`) live on the **`VideoFrameExt` trait** — `use gstreamer_video::prelude::VideoFrameExt;` or they're "method not found". Stamping the **Y plane** directly (luma 235/16 cells) means no extra element and a pipeline graph identical to T2–T6 — and works for both I420 and NV12 (both have a full-res Y plane 0).
- **VAAPI hardware encode (`QUASAR_ENCODER=va`).** AMD VCN typically exposes only the *low-power* VA entrypoint, so prefer **`vah264lpenc`** and fall back to `vah264enc` (Intel/full); the LP encoder lacks some properties (e.g. B-frames), so set encoder props **defensively** — guard each with `enc.find_property(name).is_some()` before `set_property` / `set_property_from_str`, because an unknown property otherwise panics. The VA encoders' **`bitrate` is in kbit/s** (openh264enc's is in bit/s — 2 Mbps is `2000` not `2_000_000`). They take **NV12** input (vs openh264enc's I420). Needs `mesa-va-drivers` in the image and the GPU passed in at runtime: `--device /dev/dri` (the dev image runs as **root**, so no `--group-add` — and it has no `render` group; for a non-root setup add the node's *numeric* gid via `--group-add "$(stat -c '%g' /dev/dri/renderD128)"`). Verify with `vainfo` (an H264 *encode* entrypoint) and `gst-inspect-1.0 vah264enc`. Note AMD VCN/Renoir exposes the **regular** `VAEntrypointEncSlice` (→ `vah264enc`), not the low-power one — the encoder auto-detects which element the `va` plugin registered. **Stale-registry trap:** the `va` plugin registers `vah264enc` only for a GPU present at *registry-scan* time. The dev image baked its registry at build time with **no GPU**, so a plain `ElementFactory::find`/`make` can't see the VA encoder at runtime (it reads the cached registry) — even though `gst-inspect-1.0 vah264enc` shows it (gst-inspect *forces* a registry update). Fix: force a fresh scan — point `GST_REGISTRY` at a non-existent path (the host binary does this automatically when `QUASAR_ENCODER=va`, and the Dockerfile now drops the baked `/root/.cache/gstreamer-1.0` so future images rescan at first runtime).
- **`MESA_LOADER_DRIVER_OVERRIDE=softpipe` hides the VA encoder.** The run scripts set `MESA_LOADER_DRIVER_OVERRIDE=softpipe` + `LIBGL_ALWAYS_SOFTWARE=1` for the *software* compositor path — but `softpipe` forces Mesa to load the software gallium driver **even for the amdgpu DRM node**, so the `va` plugin probes a software device (no H264 encode entrypoint) and registers **no `vah264enc`** → "no VA H264 encoder found", even with `--device /dev/dri` present and `vainfo` working. This is why VA worked in `run-t7-encode.sh` (no such override) but not `run-t7-latency.sh` (had it). The override is now gated off whenever `QUASAR_ENCODER=va` or a real `QUASAR_RENDER_NODE` is set. General rule: never force software Mesa on a hardware-VA run. The T7 overlay stamps on the CPU, so the encoder input is forced to **system-memory** NV12 (no zero-copy upload) — a deliberate instrument trade-off; zero-copy DMABuf is a T8 perf concern in tension with CPU overlay stamping.
- **uinput devices need `device_cgroup_rules` to be readable inside the container.** `devices: [/dev/uinput]` in docker-compose grants the container write access to the uinput chardev but does NOT whitelist the `/dev/input/eventN` devices that uinput creates at runtime (those have char major 13). The node-agent's fake-udev does `mknod /dev/input/eventN` inside the container, but the cgroup device ACL blocks reads — libinput silently fails to open the keyboard/mouse paths and the compositor receives zero events (no GStreamer error or warning is emitted). Fix: add `device_cgroup_rules: ['c 13:* rmw']` to the node-agent service. General rule: `devices:` only whitelists devices that exist at container start; devices born at runtime via uinput (or similar) need a `device_cgroup_rules` entry for their major number. **Diagnostic:** `ls /proc/$(pgrep quasar-node)/fd/ | grep event` — if no event device FDs appear after a session starts, libinput failed to open them. Confirm with `python3 -c "open('/dev/input/event10','rb')"` inside the container: if it raises `PermissionError: [Errno 1] Operation not permitted`, the cgroup rule is missing.
- **Relative-mouse jitter is fixed by agent-side 1ms batching + fractional accumulation (Moonlight-derived, 2026-06).** The streamed video can look smooth while the mouse *feels* jittery/steppy — the cause was bursty per-arrival uinput injection cadence + per-message `dx.round()` quantizing sub-pixel motion inconsistently (0.4+0.4+0.4 → 0+0+0). The fix is purely agent-side (no wire change): a dedicated `quasar-rel-flush` thread coalesces bursty `mm` arrivals into one `REL_X/REL_Y/SYN_REPORT` uinput write per ~1ms window (Moonlight's `MOUSE_BATCHING_INTERVAL_MS=1` design), and a fractional remainder is carried across `mm` messages so only the integer part is emitted. Do NOT tie input flush to the browser rAF — an earlier experiment did that and the video hitched (rAF couples input to render cadence and reduces the sample rate). Non-`mm` events drain pending motion synchronously before injecting so a click lands at the cursor the user saw. Knobs: `QUASAR_INPUT_BATCH_MS` (default `1`, `0` = disabled → per-arrival writes with fractional accumulation still active); `QUASAR_INPUT_CHANNEL_MODE=legacy` restores the old unreliable+unordered DataChannel for A/B. `QUASAR_INPUT_TRACE=1` enables per-`mm` `{seq, tc, recv_ms, inject_ms, dwell_ms, dx, dy}` debug logging under the `quasar.input.trace` target; the browser attaches `seq`+`tc` when `?itrace=1` (additive optional fields on `mm`, see `protocol/input.md`). Verify batching is live on session start: the agent logs `relative-mouse batching enabled (1 ms window, dedicated flush thread)`.
- **gst-interpipe across pipelines: SHARED clock + `interpipesrc do-timestamp=false` is the design of record (#68 superseded the P2-07 `do-timestamp=true` advice).** The launcher↔game swap splits a session into a per-app **source** pipeline (`compositor → … → interpipesink`) and a persistent **encode** pipeline (`interpipesrc → encoder → webrtcbin`, never restarts). Two distinct `GstPipeline`s default to independent clocks — feeding timestamps straight through with unshared clocks makes rtph264pay derive RTP timestamps the browser treats as wildly late → it **drops ~70% of frames** (the stream looks black/frozen even though `video.videoWidth` is set, frames decode, and `currentTime` advances — only `getVideoPlaybackQuality().droppedVideoFrames` reveals it). The P2-07-era fix (`do-timestamp=true`, re-stamp on arrival) turned out to be the #68 GCC-collapse trigger: arrival-time re-stamping bakes encode-side arrival jitter into RTP timestamps, and rtpgccbwe misreads a clean LAN as congested (estimate collapses to ~245 kbps, ~0.5 fps). Design of record (`runner.rs` shared `SystemClock` + shared base-time across the source/encode pipelines (never the audio pipeline, below); `pipeline.rs` sets `do-timestamp=false` explicitly): the compositor's PTS are already valid running-time in the encode pipeline and pass through untouched — arrival jitter cannot reach RTP timestamps by construction. `stream-sync` stays at its default; `restart-ts` (re-base to 0) actively *causes* mismatch and must NOT be used here. Other interpipe specifics: `interpipesink forward-eos=false` (so tearing a source down on a swap doesn't EOS the live encoder), and the encode pipeline is **never structurally touched** on a swap — only `interpipesrc.listen-to` is re-pointed (one `set_property`), which is what keeps `webrtcbin` from renegotiating (verify: the agent logs exactly **one** `offer created` for the whole session, across every swap). **Headless `running` is not enough to catch this** — a session reaches `running` on the first offer regardless of frame flow; only a real browser (or a `getVideoPlaybackQuality()` check) surfaces the drop. `gst-interpipe` is a third-party plugin (RidgeRun), built from source in `Dockerfile.dev` (v1.1.10, meson/ninja) — not in the Debian gst packages. Note: the bundled weston demo SHM clients (`weston-flower`, `weston-smoke`) render near-black on the black compositor background; use `weston-terminal` for a visibly-rendering app when eyeballing the stream.
- **Two webrtcbins in one gst::Pipeline stall the state transition (#304).** The separate-audio-video PeerConnection architecture splits audio into its own `webrtcbin` to eliminate browser A/V clock-coupling latency (~15ms measured, issue #304). The audio webrtcbin MUST live in its own `gst::Pipeline` (not the encode pipeline) — two webrtcbins sharing one pipeline's aggregate state never reach PLAYING (the session hangs at "Establishing Connection" with zero negotiation logs). The audio pipeline is created in `build_encode_pipeline`, set to READY inside the function, then set to PLAYING by `runner.rs` alongside the encode pipeline. It runs on the capture's own clock, never the shared `SystemClock` (#351): slaved to it, the PulseAudio monitor drifts ahead (~80 ppm), audiobasesrc's skew slaving never corrects a fast capture, and webrtcbin's internal `clocksync sync=true` holds each buffer until its timestamp, so after ~40 min the 200 ms capture ring buffer overruns and the browser hears ~70 ms of every ~270 ms. On the way out the sound server is stopped before the audio pipeline goes to NULL, never after (`session/teardown.rs` "Audio ordering"): `pulsesrc` waits on its server on the way down, 30 s if that server is frozen. It posts `Disconnected: Connection terminated` when the server goes, so the runner stops reporting from the audio bus first (#588); the same line from a live session (`audio-pipeline-message`) is a dead sound server. The `"input"` DataChannel is on the video webrtcbin only — input latency is unaffected by audio. Signaling carries an optional `pc` field (`"video"`/`"audio"`) on `offer`/`answer`/`ice` (additive, backwards-compatible — absent defaults to `"video"`). The browser creates two `RTCPeerConnection`s, routes signaling by `pc`, and attaches the audio track to a hidden `<audio>` element so the browser's A/V sync has no audio track to couple the video PC's jitter buffer against. `QUASAR_AUDIO_DISABLED=1` creates only the video PC (no audio m-line, no audio offer) — a diagnostic toggle that also measures the coupling delta.
- **`webrtcbin` cannot restart ICE, and a transport serves one peer for life (#535).** `webrtcbin` ignores the `ice-restart` offer option (the string is not in the plugin, through GStreamer 1.28.8), so `pipeline::restart_ice` re-sends the transport's offer: the same `o=` session one version on, the same ICE credentials, no new candidates. Its DTLS and SCTP associations belong to the first peer that connected, so a peer with new peer connections (a second browser or device, a page that resumes the session) never gets media from a re-offer. A reload is not one of these: it closes the page's peer connections, and the host ends the session on that. The agent tells a new peer from its answer (`webrtc::answer_from`, called through `runner::Negotiation::who` against the answer the runner last handed that transport: another DTLS fingerprint, or another ICE ufrag once DTLS has started on it) and gives that PC a new transport (`pipeline/transport.rs`), which sends one further offer; the same peer's answer is applied in place. **A browser answers that new transport's offer with a new ufrag and the certificate it had**, so the ufrag alone does not make a peer new: before any DTLS it is the same peer whose earlier, late answer was applied, and the transport offers again instead of being replaced. Measured, that offer differs from the old one as an ICE restart would: a new `o=` session id and new ICE credentials, and the same fingerprint (**every `webrtcbin` in a process presents one DTLS certificate**), mids, payload types, SCTP port and video SSRC. Rules that each cost a debugging session: (1) **FLUSHING must never reach the encode chain.** A push parked in a transport being torn down returns FLUSHING, and FLUSHING pauses the `queue` task upstream of the encoder for good, silently. The transport sits in a bin whose sink pad reports success once it is retired; keep that pad active until the tail is idle. (2) **Remove the old transport from the pipeline before setting it to NULL**, or its dying SCTP association reaches the session's bus and reads as the peer leaving. (3) **Never `create-offer` on a `webrtcbin` that has not made its first offer.** It waits for its sink pad's caps before `on-negotiation-needed`; an offer forced earlier (a `restart_ice` landing right after a replacement, or right at launch) has no `a=ssrc`/msid, the client decodes nothing, and the real offer never comes (`webrtc::has_offered`). (4) **Pin `msid` on the sink pad** (`transport::pin_msid`). Unset, each `webrtcbin` invents one, and a browser takes the new transport's offer for a new MediaStream: a second `track` event on a peer connection the page already wired. (5) **`webrtcbin` checks the answer's `a=fingerprint` against the certificate the peer presents in DTLS, and says nothing when they differ** (GStreamer 1.28.5 on; 1.28.4 ignored the fingerprint). Until they match, everything that transport receives is held: RTP, RTCP and the data channel. What it sends is not. The tell for a mismatch: ICE and DTLS connected, the client decodes video, input is dead because the input channel never opens, and no TWCC, PLI or NACK reaches the host; nothing on the bus and no log line from `webrtcbin` (an algorithm it does not know logs GLib's `unknown GChecksumType!`); the agent's own warning is the #577 bullet below. The compare is exact text (measured, 18 forms), and what an answer must say to pass is contract: `protocol/signaling.md` §The answer's `a=fingerprint` (amendment 29) has which line is read (the m-section it means is the section the BUNDLE group names first) and the form it takes. Behind one line of it: `sha-384` is refused because the plugin spells it `sha-284`. So the fingerprint that tells peers apart for this code (`webrtc::answer_from`) is also what the host holds a peer to. Pinned by `takeover_tests::a_peer_whose_fingerprint_is_not_its_certificates_gets_video_and_no_input_channel`: if that fails, the check is gone. (6) **A transport added mid-stream must send no RECONFIGURE upstream** (linked `NO_RECONFIGURE`, and the event dropped at its sink pad). Without that two RECONFIGURE events reach the encoder at every replacement and it renegotiates (measured; `a_takeover_mid_stream_moves_the_stream_to_the_new_peer` counts them). (7) **On the way out, the video `webrtcbin` goes to NULL before the source is stopped** (`runner::stop_source`): that releases a push a transport holds, whatever made the source wait on it. Rule 9 means none is held any more; the order stays as the cheap guard. (8) **Link the tail to a transport added mid-stream only once that transport's pads are active.** The link makes the tail resend its sticky events on the next push, and a pad that is not active refuses them FLUSHING: that fails the push inside `check_sticky`, before any probe or chain function runs, and pauses the encode chain for good. The new transport then never gets caps, so it never offers either. The window is under a millisecond, about one replacement in fifty; `takeover_tests::every_replacement_transport_makes_its_offer` holds it open. (9) **No transport gets RTP until its peer has connected, the launch one included** (the tail's DROP probe stays until `connection-state` is `connected`; a keyframe is forced then and the probe goes at that keyframe, so the peer is never sent the rest of a GOP it has none of). Held RTP parks the encode chain's streaming thread, and a size step or an app swap in that time sends an allocation query that waits behind it with the source's streaming thread: the swap then blocks the runner inside `interpipesrc`'s `listen-to` setter, where no stop reaches it. A webrtcbin test peer is stricter than a browser in one way: it rejects a second offer whose H.264 `profile-level-id` differs from the first (openh264enc changes level when its bitrate is written live). And it is no second browser unless it is made one: it presents the process's certificate. `takeover_tests::Peer::another_browser` gives it its own, which takes two things by hand. The certificate must be set on the peer's `dtlsdec` (`pem`) while that element is still in NULL, so as `webrtcbin` adds it (`deep-element-added`): set later, the peer advertises it and presents the process's one. And a `webrtcbin` given a certificate states a wrong fingerprint for it (it hashes the key in the PEM along with the certificate), so the test writes the true one into the peer's answers. The host is never given a certificate, so its offers are right. Regression tests: `session::pipeline::takeover_tests` (they need libnice and interpipe, so they run in `quasar-agent-dev` and skip in the devtools image); real Chrome and the real web client: `scripts/harness/run-takeover-peers.sh`.
- **The fingerprint verdict shows only as blocked pads inside `webrtcbin` (#577).** On 1.28.8 a failed check changes nothing a caller is meant to read (measured against a forged and an honest peer): `connection-state`, the DTLS transport's `state` and `dtlsdec`/`dtlsenc`'s `connection-state` all read `connected`, `remote-certificate` is set, and the bus is silent. `webrtcbin` holds a transport's inbound side with blocking probes on the three source pads of its `TransportReceiveBin` (`rtp_src`, `rtcp_src`, `data_src`) and removes them only in `validate_transport_fingerprint`, so `gst_pad_is_blocked` on `rtp_src` of the `TransportReceiveBin` is the verdict, and that is the pad the agent reads (`webrtc::holds_inbound`). `data_src` is not the pad to read: on a `webrtcbin` with a data channel it carries a second block, for SCTP, that `webrtcbin` lifts later on its task thread. That function has two callers in 1.28.8: `webrtcbin`'s handler of the DTLS transport's `state`, and the application of a description, which calls it only when signaling returns to `stable`: on every answer applied, not on an offer. So a transport the agent warned about could pass later, if a later answer on the same transport named the right certificate; the agent never applies one today (a changed fingerprint goes to a new transport, `webrtc::answer_from`). Read it from a handler of the DTLS transport's `notify::state` connected `after`, and connected before any answer (the transport exists from `signaling-state` `have-local-offer`): `webrtcbin` makes the check in its own handler of that signal, on the same thread. Read at `connection-state` `connected`, a read of `data_src` races that SCTP task, not the check: an honest peer was caught with `rtp_src` open and `data_src` still blocked, two runs of two. The agent warns once per transport, `token="transport-peer-fingerprint-mismatch"` (`webrtc::warn_on_fingerprint_mismatch`). The type and pad names are private to the plugin: if a GStreamer bump renames them the agent goes quiet, not wrong, and `takeover_tests::a_peer_whose_fingerprint_is_not_its_certificates_gets_video_and_no_input_channel` goes red.

# Encoder property gotchas (Rust + gst-inspect, learned 2026-06)

- **Verify every encoder property against `gst-inspect-1.0` inside the dev image with the GPU attached before coding it** — externally-researched property lists hallucinate. Confirmed real vs fictional: `vah264enc` has **no `tune`, no `quality-level`, no `max-bitrate`** (those are legacy `gstreamer-vaapi` names; the `va` plugin uses `target-usage`/`rate-control`/`cpb-size`); NVENC lookahead is **`rc-lookahead`** (not "lookahead-depth"); `aq-strength` only acts when **`spatial-aq=true`**; `temporal-aq` wants lookahead (= latency, avoid for streaming); there is **no `scd` element** (the scene-change element is `scenechange`). Inspect needs the device or the element isn't registered at all (`--device /dev/dri` / `--gpus all`, fresh `GST_REGISTRY`).
- **VP9 is a hardware dead end here**: AMD VCN and NVENC both *decode* VP9 but neither *encodes* it. The future codec lever is **AV1** (RTX 5090 NVENC has it; AMD needs VCN4+; Renoir does not).
- **A suspiciously *tight* `encode_ms` distribution means a clocked bottleneck, not load.** Aux-host Renoir VCN sits at p50 19.24 / p95 20.08 ms (→ 45 fps ceiling) with the GPU in `power_dpm_force_performance_level=auto` — suspected low VCN DPM clock; test `echo high > /sys/class/drm/card0/device/power_dpm_force_performance_level` (host root) before tuning encoder properties on that box. The 5090 encodes the same content in p50 2.0 ms at a flat 60 fps.

## Standalone Vulkan HEVC pipelines must pin `video/x-h265,profile=main` (2026-08-22)
`vulkanh265enc` builds its src template from driver caps and advertises `main-444`, which its own
`H265ProfileMap` cannot map. A bare `... ! vulkanh265enc ! h265parse ! fakesink` negotiates
`main-444` and fails with `Video profile format not supported (-1000023003):
vkGetPhysicalDeviceVideoCapabilitiesKHR` at `new_sequence`. This looks exactly like a driver
regression and was chased twice as one. The node-agent always pins `profile=main`
(`pipeline/caps.rs`), so live sessions are unaffected. Any hand-written probe must pin it too.
Also: the `qses` headless Linux Chrome peer cannot decode HEVC and REJECTS the video m-line
(`webrtcbin: Invalid bundle id 1`), which presents as an encode-src ring stall (#503/#504), so
h265 live validation needs a macOS/Windows Chrome. The report,
`docs/reports/2026-08-22-vulkanscale-validation/H265-PROFILE-CAPS.md`, was deliberately not carried over to the public repository.

## Ad-hoc `docker exec gst-launch` in a compose-run agent container fails EGL (2026-08-28)
The compose env passes blank-but-SET `MESA_LOADER_DRIVER_OVERRIDE=` (and friends); the agent
sanitizes these internally, but an ad-hoc `docker exec ... gst-launch-1.0` inherits them and
dies with EGL "failed to create dri2 screen". Prefix probes with `env -u MESA_LOADER_DRIVER_OVERRIDE -u LIBGL_ALWAYS_SOFTWARE`
(or run a fresh `docker run --device /dev/dri` from the image instead).
