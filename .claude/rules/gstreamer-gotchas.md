# GStreamer-rs gotchas (Rust, not gst-launch)

These bit real tickets — gst-launch is more forgiving than the Rust GObject API.

- **Never capture a strong element clone into a closure attached to that same element (pad probe or signal) — it's a GObject ref cycle GLib never collects.** This leaked ~505 MiB VRAM + ~27 MiB RSS per session (2026-07-25): the leaked element pins its closures' Arcs (SessionMetrics) and its cached GstContexts (the session's GstVulkanDevice/CUDA/VA display). Read the element via `pad.parent_element()` inside the callback instead; for element↔Arc cross cycles (encoder pads hold `SessionMetrics`, ABR hooks hold the encoder) break them deterministically at teardown (`SessionMetrics::clear_hooks()` drop guard in `run_blocking`). Regression tests: `session::pipeline::probes::tests`.
- **Elements returned from `request-aux-sender` / `request-post-rtp-aux-sender` signal closures must be handed back FLOATING** (`g_object_force_floating` before `to_value()`): the C side ref_sinks the return on bin-add expecting a C-handler floating ref; gstreamer-rs sinks at construction, so a plain strong handle leaks one ref per session (leaked rtpgccbwe → AbrLoop → encoder chain).
- **Leak triage recipe:** `GST_TRACERS='leaks(filters=GstObject)' GST_DEBUG=GST_TRACER:7 GST_LEAKS_TRACER_SIG=1`, then `docker kill -s USR1 <agent>` dumps `object-alive` lines (name + live ref-count). The vendored `/opt/gst` build has NO coretracers — copy the Fedora one in first: `docker exec <c> cp /usr/lib64/gstreamer-1.0/libgstcoretracers.so /opt/gst/lib64/gstreamer-1.0/` + container restart. Fedora's tracer has no stack-trace support; positional filter syntax (`leaks(GstElement)`) fails on 1.28 — use `filters=`.
- **Enum-typed element properties** (openh264enc `rate-control`/`complexity`, rtph264pay `aggregate-mode`, videotestsrc `pattern`) MUST be set with `.property_from_str("name", "value")`. `gst-launch` coerces integers; the Rust setter rejects an `i32` and panics at `build()`. (A copy-the-gst-launch-line port will compile and then panic at runtime.)
- `webrtcbin` must be at least `READY` before `create-data-channel` (it is "closed" in `NULL`).
- `create-data-channel` returns a `GstWebRTCDataChannel`, which gstreamer-webrtc 0.23 does not bind as a typed struct — emit untyped (`emit_by_name_with_values`) and upcast the returned `Value` to `glib::Object`.
- ICE may jump `Checking → Completed`, skipping `Connected`. Treat both `Connected` and `Completed` as transport-established.
- `waylanddisplaysrc` produces **1 fps** unless a framerate is requested downstream — it honors whatever caps ask for, but defaults low if nothing does. Always put `framerate=N/1` in the caps after the source (`videotestsrc` defaults to 30, which is why a test-src pipeline hides this). It is also damage/rate-driven, so it emits steady frames at the requested rate even for a static scene (no `videorate` needed).
- **DataChannel init parameters** (ordered, max-retransmits, etc.) are passed as a `gst::Structure` second argument to `create-data-channel`. The default `"input"` DataChannel is now **reliable + ordered** (`ordered:true`, SCTP default retransmission) — the input-jitter investigation (2026-06) validated this against Moonlight's `ENET_PACKET_FLAG_RELIABLE` relative-mouse path; a dropped `mm` sample is costlier to perceived smoothness than the small head-of-line delay. The Phase-0 unreliable+unordered config (`gst::Structure::builder("application/data-channel").field("ordered", false).field("max-retransmits", 0i32).build()`) is retained as an A/B fallback via `QUASAR_INPUT_CHANNEL_MODE=legacy`. The structure name is ignored by webrtcbin; only the fields matter.
- **`on-message-string` vs `on-message-data`**: GstWebRTCDataChannel has two message signals. JSON input events are strings — connect to `on-message-string`. Raw bytes use `on-message-data`.
- **Replying on the DataChannel from its own signal closure (T7 pong).** The channel is an untyped `glib::Object` (not bound as a typed struct), and `glib::Object`'s `WeakRef` is **not `Send`** — capturing it in a `connect(...)` closure fails to compile (`*mut c_void cannot be sent between threads`). The emitter is always the signal's first value, so get the channel from `values[0].get::<glib::Object>()` inside the handler and `emit_by_name::<()>("send-string", &[&json])` on it — no capture needed.
- **Writing into a frame in a pad probe (T7 overlay).** `PadProbeInfo::buffer()` is read-only; `buffer_mut()` returns `&mut gst::Buffer` (owned), not a `BufferRef` — call `.make_mut()` on it to get the `&mut gst::BufferRef` that `VideoFrameRef::from_buffer_ref_writable(buffer, &VideoInfo)` needs (it copies iff the buffer is shared, which it isn't for a freshly converted I420 frame). The frame accessors (`width`/`height`/`plane_stride`/`plane_data_mut`) live on the **`VideoFrameExt` trait** — `use gstreamer_video::prelude::VideoFrameExt;` or they're "method not found". Stamping the **Y plane** directly (luma 235/16 cells) means no extra element and a pipeline graph identical to T2–T6 — and works for both I420 and NV12 (both have a full-res Y plane 0).
- **VAAPI hardware encode (`QUASAR_ENCODER=va`).** AMD VCN typically exposes only the *low-power* VA entrypoint, so prefer **`vah264lpenc`** and fall back to `vah264enc` (Intel/full); the LP encoder lacks some properties (e.g. B-frames), so set encoder props **defensively** — guard each with `enc.find_property(name).is_some()` before `set_property` / `set_property_from_str`, because an unknown property otherwise panics. The VA encoders' **`bitrate` is in kbit/s** (openh264enc's is in bit/s — 2 Mbps is `2000` not `2_000_000`). They take **NV12** input (vs openh264enc's I420). Needs `mesa-va-drivers` in the image and the GPU passed in at runtime: `--device /dev/dri` (the dev image runs as **root**, so no `--group-add` — and it has no `render` group; for a non-root setup add the node's *numeric* gid via `--group-add "$(stat -c '%g' /dev/dri/renderD128)"`). Verify with `vainfo` (an H264 *encode* entrypoint) and `gst-inspect-1.0 vah264enc`. Note AMD VCN/Renoir exposes the **regular** `VAEntrypointEncSlice` (→ `vah264enc`), not the low-power one — the encoder auto-detects which element the `va` plugin registered. **Stale-registry trap:** the `va` plugin registers `vah264enc` only for a GPU present at *registry-scan* time. The dev image baked its registry at build time with **no GPU**, so a plain `ElementFactory::find`/`make` can't see the VA encoder at runtime (it reads the cached registry) — even though `gst-inspect-1.0 vah264enc` shows it (gst-inspect *forces* a registry update). Fix: force a fresh scan — point `GST_REGISTRY` at a non-existent path (the host binary does this automatically when `QUASAR_ENCODER=va`, and the Dockerfile now drops the baked `/root/.cache/gstreamer-1.0` so future images rescan at first runtime).
- **`MESA_LOADER_DRIVER_OVERRIDE=softpipe` hides the VA encoder.** The run scripts set `MESA_LOADER_DRIVER_OVERRIDE=softpipe` + `LIBGL_ALWAYS_SOFTWARE=1` for the *software* compositor path — but `softpipe` forces Mesa to load the software gallium driver **even for the amdgpu DRM node**, so the `va` plugin probes a software device (no H264 encode entrypoint) and registers **no `vah264enc`** → "no VA H264 encoder found", even with `--device /dev/dri` present and `vainfo` working. This is why VA worked in `run-t7-encode.sh` (no such override) but not `run-t7-latency.sh` (had it). The override is now gated off whenever `QUASAR_ENCODER=va` or a real `QUASAR_RENDER_NODE` is set. General rule: never force software Mesa on a hardware-VA run. The T7 overlay stamps on the CPU, so the encoder input is forced to **system-memory** NV12 (no zero-copy upload) — a deliberate instrument trade-off; zero-copy DMABuf is a T8 perf concern in tension with CPU overlay stamping.
- **uinput devices need `device_cgroup_rules` to be readable inside the container.** `devices: [/dev/uinput]` in docker-compose grants the container write access to the uinput chardev but does NOT whitelist the `/dev/input/eventN` devices that uinput creates at runtime (those have char major 13). The node-agent's fake-udev does `mknod /dev/input/eventN` inside the container, but the cgroup device ACL blocks reads — libinput silently fails to open the keyboard/mouse paths and the compositor receives zero events (no GStreamer error or warning is emitted). Fix: add `device_cgroup_rules: ['c 13:* rmw']` to the node-agent service. General rule: `devices:` only whitelists devices that exist at container start; devices born at runtime via uinput (or similar) need a `device_cgroup_rules` entry for their major number. **Diagnostic:** `ls /proc/$(pgrep quasar-node)/fd/ | grep event` — if no event device FDs appear after a session starts, libinput failed to open them. Confirm with `python3 -c "open('/dev/input/event10','rb')"` inside the container: if it raises `PermissionError: [Errno 1] Operation not permitted`, the cgroup rule is missing.
- **Relative-mouse jitter is fixed by agent-side 1ms batching + fractional accumulation (Moonlight-derived, 2026-06).** The streamed video can look smooth while the mouse *feels* jittery/steppy — the cause was bursty per-arrival uinput injection cadence + per-message `dx.round()` quantizing sub-pixel motion inconsistently (0.4+0.4+0.4 → 0+0+0). The fix is purely agent-side (no wire change): a dedicated `quasar-rel-flush` thread coalesces bursty `mm` arrivals into one `REL_X/REL_Y/SYN_REPORT` uinput write per ~1ms window (Moonlight's `MOUSE_BATCHING_INTERVAL_MS=1` design), and a fractional remainder is carried across `mm` messages so only the integer part is emitted. Do NOT tie input flush to the browser rAF — an earlier experiment did that and the video hitched (rAF couples input to render cadence and reduces the sample rate). Non-`mm` events drain pending motion synchronously before injecting so a click lands at the cursor the user saw. Knobs: `QUASAR_INPUT_BATCH_MS` (default `1`, `0` = disabled → per-arrival writes with fractional accumulation still active); `QUASAR_INPUT_CHANNEL_MODE=legacy` restores the old unreliable+unordered DataChannel for A/B. `QUASAR_INPUT_TRACE=1` enables per-`mm` `{seq, tc, recv_ms, inject_ms, dwell_ms, dx, dy}` debug logging under the `quasar.input.trace` target; the browser attaches `seq`+`tc` when `?itrace=1` (additive optional fields on `mm`, see `protocol/input.md`). Verify batching is live on session start: the agent logs `relative-mouse batching enabled (1 ms window, dedicated flush thread)`.
- **gst-interpipe across pipelines: SHARED clock + `interpipesrc do-timestamp=false` is the design of record (#68 superseded the P2-07 `do-timestamp=true` advice).** The launcher↔game swap splits a session into a per-app **source** pipeline (`compositor → … → interpipesink`) and a persistent **encode** pipeline (`interpipesrc → encoder → webrtcbin`, never restarts). Two distinct `GstPipeline`s default to independent clocks — feeding timestamps straight through with unshared clocks makes rtph264pay derive RTP timestamps the browser treats as wildly late → it **drops ~70% of frames** (the stream looks black/frozen even though `video.videoWidth` is set, frames decode, and `currentTime` advances — only `getVideoPlaybackQuality().droppedVideoFrames` reveals it). The P2-07-era fix (`do-timestamp=true`, re-stamp on arrival) turned out to be the #68 GCC-collapse trigger: arrival-time re-stamping bakes encode-side arrival jitter into RTP timestamps, and rtpgccbwe misreads a clean LAN as congested (estimate collapses to ~245 kbps, ~0.5 fps). Design of record (`runner.rs` shared `SystemClock` + shared base-time across source/encode/audio pipelines; `pipeline.rs` sets `do-timestamp=false` explicitly): the compositor's PTS are already valid running-time in the encode pipeline and pass through untouched — arrival jitter cannot reach RTP timestamps by construction. `stream-sync` stays at its default; `restart-ts` (re-base to 0) actively *causes* mismatch and must NOT be used here. Other interpipe specifics: `interpipesink forward-eos=false` (so tearing a source down on a swap doesn't EOS the live encoder), and the encode pipeline is **never structurally touched** on a swap — only `interpipesrc.listen-to` is re-pointed (one `set_property`), which is what keeps `webrtcbin` from renegotiating (verify: the agent logs exactly **one** `offer created` for the whole session, across every swap). **Headless `running` is not enough to catch this** — a session reaches `running` on the first offer regardless of frame flow; only a real browser (or a `getVideoPlaybackQuality()` check) surfaces the drop. `gst-interpipe` is a third-party plugin (RidgeRun), built from source in `Dockerfile.dev` (v1.1.10, meson/ninja) — not in the Debian gst packages. Note: the bundled weston demo SHM clients (`weston-flower`, `weston-smoke`) render near-black on the black compositor background; use `weston-terminal` for a visibly-rendering app when eyeballing the stream.
- **Two webrtcbins in one gst::Pipeline stall the state transition (#304).** The separate-audio-video PeerConnection architecture splits audio into its own `webrtcbin` to eliminate browser A/V clock-coupling latency (~15ms measured, issue #304). The audio webrtcbin MUST live in its own `gst::Pipeline` (not the encode pipeline) — two webrtcbins sharing one pipeline's aggregate state never reach PLAYING (the session hangs at "Establishing Connection" with zero negotiation logs). The audio pipeline is created in `build_encode_pipeline`, set to READY inside the function, then set to PLAYING by `runner.rs` alongside the encode pipeline (both share the same `gst::SystemClock` + base time for coherent RTP timestamps). The audio pipeline is torn down on all exit paths via a `stop_audio` closure. The `"input"` DataChannel is on the video webrtcbin only — input latency is unaffected by audio. Signaling carries an optional `pc` field (`"video"`/`"audio"`) on `offer`/`answer`/`ice` (additive, backwards-compatible — absent defaults to `"video"`). The browser creates two `RTCPeerConnection`s, routes signaling by `pc`, and attaches the audio track to a hidden `<audio>` element so the browser's A/V sync has no audio track to couple the video PC's jitter buffer against. `QUASAR_AUDIO_DISABLED=1` creates only the video PC (no audio m-line, no audio offer) — a diagnostic toggle that also measures the coupling delta.

# Encoder property gotchas (Rust + gst-inspect, learned 2026-06)

- **Verify every encoder property against `gst-inspect-1.0` inside the dev image with the GPU attached before coding it** — externally-researched property lists hallucinate. Confirmed real vs fictional: `vah264enc` has **no `tune`, no `quality-level`, no `max-bitrate`** (those are legacy `gstreamer-vaapi` names; the `va` plugin uses `target-usage`/`rate-control`/`cpb-size`); NVENC lookahead is **`rc-lookahead`** (not "lookahead-depth"); `aq-strength` only acts when **`spatial-aq=true`**; `temporal-aq` wants lookahead (= latency, avoid for streaming); there is **no `scd` element** (the scene-change element is `scenechange`). Inspect needs the device or the element isn't registered at all (`--device /dev/dri` / `--gpus all`, fresh `GST_REGISTRY`).
- **VP9 is a hardware dead end here**: AMD VCN and NVENC both *decode* VP9 but neither *encodes* it. The future codec lever is **AV1** (RTX 5090 NVENC has it; AMD needs VCN4+; Renoir does not).
- **A suspiciously *tight* `encode_ms` distribution means a clocked bottleneck, not load.** Hermes Renoir VCN sits at p50 19.24 / p95 20.08 ms (→ 45 fps ceiling) with the GPU in `power_dpm_force_performance_level=auto` — suspected low VCN DPM clock; test `echo high > /sys/class/drm/card0/device/power_dpm_force_performance_level` (host root) before tuning encoder properties on that box. The 5090 encodes the same content in p50 2.0 ms at a flat 60 fps.

## Standalone Vulkan HEVC pipelines must pin `video/x-h265,profile=main` (2026-08-22)
`vulkanh265enc` builds its src template from driver caps and advertises `main-444`, which its own
`H265ProfileMap` cannot map. A bare `... ! vulkanh265enc ! h265parse ! fakesink` negotiates
`main-444` and fails with `Video profile format not supported (-1000023003):
vkGetPhysicalDeviceVideoCapabilitiesKHR` at `new_sequence`. This looks exactly like a driver
regression and was chased twice as one. The node-agent always pins `profile=main`
(`pipeline/caps.rs`), so live sessions are unaffected. Any hand-written probe must pin it too.
Also: the `qses` headless Linux Chrome peer cannot decode HEVC and REJECTS the video m-line
(`webrtcbin: Invalid bundle id 1`), which presents as an encode-src ring stall (#503/#504), so
h265 live validation needs a macOS/Windows Chrome. Report:
`docs/reports/2026-08-22-vulkanscale-validation/H265-PROFILE-CAPS.md`.

## Ad-hoc `docker exec gst-launch` in a compose-run agent container fails EGL (2026-08-28)
The compose env passes blank-but-SET `MESA_LOADER_DRIVER_OVERRIDE=` (and friends); the agent
sanitizes these internally, but an ad-hoc `docker exec ... gst-launch-1.0` inherits them and
dies with EGL "failed to create dri2 screen". Prefix probes with `env -u MESA_LOADER_DRIVER_OVERRIDE -u LIBGL_ALWAYS_SOFTWARE`
(or run a fresh `docker run --device /dev/dri` from the image instead).
