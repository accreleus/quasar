# RH05 operator journey and remaining manual work

This handoff describes the RH05 behavior on the initiative integration branch. It is not a deployment guide or a claim that the current production stack runs this branch. Use the versioned [install and multi-host guide](../../deploy/README.md) for initial deployment, [configuration reference](../configuration.md) for environment and mount inputs, and [#333](https://github.com/accreleus/quasar/issues/333) for the approved product scope. The #346 combined acceptance report must link the exact commit, image digests, schema version and live screenshots before this handoff is called complete.

## 1. Enroll and inspect the host

Install or enroll the host using Admin → Fleet → Enroll host and the existing installer. RH05 begins **after** the agent has enrolled; it does not mint bootstrap credentials, install GPU drivers, change device passthrough, add bind mounts or replace Quasar's platform containers. Keep the agent identity and owner state on its persistent volume. Confirm the host's connection, GPU evidence and readiness in Fleet before selecting app placement. A visible device in `/sys` alone does not establish that the agent can open it. If evidence is missing or ambiguous, Automatic remains pending and the Fleet view should name a remedy.

After migration 0088, a previously draining host can carry a `legacy_drain` hold, even if a platform operation was also underway. Inspect **Admission restrictions** on that host. Release operator drain only when that particular hold is no longer wanted; doing so does not remove a platform, recovery or idle-apply hold. A host stays unavailable while any restriction remains. Do not use uncordon as a repair for an unknown configuration attempt or home conflict.

## 2. Choose configuration sources and read the result

In Fleet → Host Settings, a supported setting can use **Automatic** (only on catalog-approved keys), **Deployment setting**, or an **Explicit value**. Existing installations keep their deliberate behavior until changed. Clearing a legacy explicit override selects the deployment fallback; it does not select Automatic. The deployment fallback is resolved by the agent from its current environment and existing detection rules, so a catalog display default is not proof of its actual value. New enrolled installations select Automatic for supported hardware keys, subject to accessible-device and probe evidence. RH05 does not automatically tune GOP, queues, ABR or concurrency.

Save and then read the status again. `Pending` means desired intent is stored, possibly while the host is offline. `Applied` requires authenticated evidence for the stated **next-session** or **post-restart** scope. A running session keeps its previous next-session snapshot. `Upgrade required` means an older agent cannot prove or perform that RH05 capability. A failed group has its own error and Retry action; one image failure need not hold an unrelated configuration group. Check **configuration**, **app preparation** and **host readiness** separately. None is a synonym for either of the others.

## 3. Approve a disruptive change only after review

For a restart-required hardware group, inspect the resolved candidate and current prerequisites, then request **Apply when idle**. The request stops new assignments to that host while already assigned, starting, running, stopping and local sessions finish. It also waits for conflicting preparation and confirmed cleanup. A timeout never kills a player session to make the host idle. An unrelated safe edit may complete without changing this approval; a relevant hardware value or evidence change supersedes an **unstarted** approval and requires a fresh review.

If the approval waits on **conflicting preparation** while no preparation is actually running — for example a Steam template warmup that failed because the hardware change you are approving is not applied yet — turn off **Settings → Library → Sources → Steam → Prepare Steam for faster first launch**, let the apply finish, then turn it back on so preparation runs on the applied configuration. Existing homes, templates and running sessions are unaffected by that switch.

**Every control-plane restart expires an unstarted approval.** Saved settings remain pending; review the current candidate and approve again. A supported database restore is performed with the stack stopped and has the same reapproval result. An already started agent attempt is reconciled from its durable journal rather than executed again from an approval row. If cancellation is requested while a grant may already be in flight, the console can say cancellation is pending until agent evidence proves whether execution started. Completion or cancellation releases only that attempt's admission restriction. If recovery is uncertain, leave admission protected and follow its displayed remedy; do not assume an acknowledgement or reconnect proves application.

## 4. Select apps and understand home locality

In each parent app's **Placement** tab, choose **All eligible hosts** for dynamic membership or a fixed host set. A newly eligible enrolled host joins the dynamic set after its prerequisites are satisfied. A derived game tile inherits its parent selection. Placement controls new launch eligibility as well as preparation; a cached image does not grant permission to run on an unselected host. Removing a host from placement blocks subsequent reservations and does not delete the app image or home. Sessions accepted before removal may finish normally.

For a managed-home app, the existing per-user, per-parent-app home has one owning host. Selection cannot silently create a blank replacement on another host. For the same reason, a host's home root cannot be changed while existing managed homes would fall outside it: the settings edit is refused, and an agent started with a different deployment root refuses to mount a home outside it. Move the homes first. A first launch claims ownership transactionally. When older locations are uncertain or divergent, Admin's paginated home-claim read surfaces a protected repair conflict; user launch refusal gives a safe explanation. Preserve every conflicting copy. RH05 does not merge, migrate or delete homes to resolve the conflict. A tombstoned home remains unavailable until exact garbage-collection confirmation; do not treat that as a launch retry opportunity. Portable homes and audited repair remain later work ([#332](https://github.com/accreleus/quasar/issues/332) and [#347](https://github.com/accreleus/quasar/issues/347)).

## 5. Read preparation and use explicit cleanup

The selected managed image version is prepared on the selected host by the existing image Ensurer. Requirements from multiple apps combine; a custom app using an adopted managed image participates. A truly unmanaged custom image is identified as unmanaged and retains the existing operator-managed image responsibility. Existing manual/notify/auto adoption and version pins still control which version is eligible. Preparation is not permission to upgrade an app or downgrade its persistent data.

A **lazy** adoption is prepared on first launch instead of ahead of time: after the launch is accepted, the selected host pulls the pinned image (or builds the template) and the session starts once that host reports the exact version ready. The player sees the loader during that time; a first pull of a large image can take minutes. A failure, timeout or host reconnect fails only that launch, and the next launch tries again (Retry does not apply to lazy images). After the first launch the image is managed on that host like an eager one.

Steam preparation retains its compatible template and new-home seeding. A new, unambiguous empty home can report **reflink**, **copy** or **cold**. Only actual reflink use can claim shared-storage savings. Copy and cold are valid visible fallbacks; a missing compatible template does not indefinitely block a valid launch. Existing nonempty homes are never rewritten by a later template.

Image removal is a separate, explicit Admin action. Review the host's current candidate and its blockers, then request cleanup of the exact managed image identity. Current app requirements, any container including a stopped container, pending launch/image/template work, unknown inventory and the previous successfully prepared version can block it. A new reference after preview can invalidate the request. A `202` means an attempt was accepted, **not** that bytes were removed; inspect its terminal result. Only a confirmed `removed` result and fresh inventory establish removal. Refresh stale previews. Cleanup never deletes a managed home.

## RH06 and other work still outside RH05

RH06 owns first-host and additional-host enrollment automation, deployment identity, credentials, mount/device provisioning and Quasar platform-image replacement. RH05 does not reconfigure those bootstrap inputs. Session adoption across agent replacement belongs to RH03/RH04; private registry support is [#9](https://github.com/accreleus/quasar/issues/9), performance and concurrency optimization is [#331](https://github.com/accreleus/quasar/issues/331), and portable homes is [#332](https://github.com/accreleus/quasar/issues/332). Milestone acceptance does not itself authorize promotion, release, image publication or changes to a shared deployed stack.
