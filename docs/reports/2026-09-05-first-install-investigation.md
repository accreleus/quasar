## Recommended installation and recovery experience

**Recommendation: make the supported installation a generated, complete stack with an agent that continuously reconciles its prerequisites.** The operator supplies intent (storage, access address, and optionally which GPU); Quasar owns internal paths, loader configuration, matching drivers, progress, retries and diagnosis. Keep Compose as the deployment format, but stop making users assemble overlays or maintain the runtime defaults themselves.

This is a proposed design, grounded in the failure inventory below. It is not implemented or live-validated by this investigation. The earlier landing-order table is the delivery breakdown; this section states what those changes should produce.

### 1. Give users one complete installation artifact

For Unraid, the supported output should be one complete Compose file plus an environment template with explicit credential-replacement instructions. Selecting NVIDIA must produce a file that already includes all required GPU requests and persistent storage. There must be no second overlay to remember, and no shell expressions masquerading as environment values. The Linux shell installer and Unraid file-import route should consume the same versioned installation definition.

Ask only for:

- Where application data should live; use platform-appropriate defaults.
- How people will reach Quasar: LAN access or an existing reverse proxy, with address/ports where needed.
- GPU selection when multiple usable GPUs exist. On a browser-only wizard, accept the vendor choice provisionally; a host-side check verifies it before deployment.
- An optional data ownership override. Detect or default it for the normal platform path.

Put advanced encoder, transport, logging and tuning overrides behind an advanced interface. They are legitimate choices, but none should be required to get the first stream. Existing Fleet settings should remain the place to change supported live settings. Show the selected release clearly, using the same release manifest as the self-update feature once that work is ready; do not introduce another independent release selector.

Generate secrets once, store them durably, and preserve them on rerun. Prefer local host generation through an installer or Unraid integration. Per the operator’s subsequent correction, standalone files must contain blank credentials and instructions to generate and paste real values. Do not generate usable credentials in the browser. Never return commands in a file labelled ready to use. Validate DB connection serialization rather than depending on operators choosing URI-safe passwords.

**Success criterion:** a new user needs only the documented credential/image selections for copied files; running the installer again does not change their credentials, erase data, or replace their selected release unexpectedly.

### 2. Separate host preparation from container self-configuration

Use a host-side installation check for things a container cannot repair after creation: Docker/Compose compatibility, image availability, NVIDIA toolkit, required device nodes, selected storage and mount permissions. Report all actionable problems together before starting the stack. Optional diagnostics such as kernel-log access must not prevent an otherwise supported installation from starting.

Inside the images, establish fixed paths and defaults automatically. The agent entrypoint sets loader search paths before exec; the agent resolves the selected GPU once and uses that same identity for encoding, provisioning and child-container GPU access. Removing a Compose environment key must not revert production audio to a development image or enrollment identity to temporary storage.

For CP storage, retain named volumes as the simplest default. For an Unraid host bind, add a small identity-preparation wrapper that prepares only Quasar-owned state and runtime directories, switches to the intended uid/gid, and execs Go. Check both persistent state and the private setup-token directory together. If ACLs, read-only storage or user-namespace mappings make this impossible, report the exact operation and path; do not suggest an unrelated uid override that creates the next failure.

**Success criterion:** standard 99:100 and 1000:1000 storage layouts both start without user-supplied `user:`, tmpfs ownership, or token-path fixes.

### 3. Turn driver provisioning into a recoverable background operation

Treat matching graphics userspace as a prerequisite Quasar maintains throughout the agent's life, rather than a one-shot startup attempt. The reconciliation loop observes the selected GPU/kernel driver and existing artifact, prepares missing content, verifies it, publishes it atomically, and rechecks readiness. A restart re-enters the same operation safely.

| Situation | Recommended automatic response | What the user sees |
| --- | --- | --- |
| Required driver content is absent | Fetch the matching version into persistent staging, verify integrity and completeness, then publish it. | “Preparing NVIDIA graphics support — downloading, 42%. No action needed.” |
| Network interruption or temporary server error | Bounded backoff with jitter; retry automatically. Resume a partial download only if server identity/range checks preserve integrity; otherwise restart that artifact safely. | Current phase, last error and next retry; a Retry now action. |
| Agent is killed during preparation | Recover staging on next start and reacquire ownership without manual file deletion. For local shared storage, prefer a process-held kernel lock; otherwise use a verified lease/owner design appropriate to the volume backend. | Preparation continues or restarts; no fictitious “other agent” requiring guesswork. |
| Another live process is preparing the same artifact | Observe/wait with a bounded recheck; do not start a competing writer. | “Graphics preparation is already running,” with fresh progress where available. |
| No space or permission denied | Stop destructive/repetitive attempts, retain valid existing artifacts, and recheck after correction. | Required space or exact path/identity problem and the relevant remedy. |
| Integrity verification fails | Discard/quarantine the failed candidate, retain the last valid artifact, and stop automatic acceptance. | Integrity failure; never generic package-install advice or automatic disabling of verification. |
| New content needs a process restart | Use the existing quiescence barrier and a bounded restart plan. During first install, restart automatically; with active sessions, defer until idle. Persist attempt limits to prevent restart loops. | “Graphics support ready; restarting agent” or “Will finish when active sessions end.” |

Known host-wide actions such as driver installation, Docker daemon restart, host reboot or security-policy changes should remain explicit operator steps. Automatic recovery should operate on Quasar-owned artifacts and processes; it should not restart unrelated Unraid containers to make its own install work.

**Success criterion:** killing the agent during download or extraction and restarting it eventually produces a usable host without deleting a lock or volume by hand.

### 4. Verify what the app receives, not just what the agent can see

Establish one validated mapping between agent paths and Docker-host mount sources. Prefer passing the resolved Docker volume identity to child containers for named volumes, avoiding dependence on the host's private Docker storage layout. For bind mounts, inspect and verify the source/destination relationship once and retain that provenance. Self-ID discovery should verify its candidate rather than accepting any hex string in mountinfo; keep an explicit override for unusual installations as an escape hatch, not a normal setup question.

Apply the same checks to driver content, application homes and runtime sockets. A writable directory inside the agent is not proof that it is persistent or visible to a child. When required mapping is unresolved, keep the agent connected for diagnosis and refuse the affected launch with that reason.

Before claiming GPU readiness, run a small bounded diagnostic child using the same launch policy, selected devices, uid/groups and driver mounts as real apps. Verify hardware Vulkan/EGL rendering and access to the shared runtime directory. Validate 32-bit libraries by architecture and driver version, not filename alone. Recheck compatibility for each actual app image digest where needed; one diagnostic image cannot certify every custom app.

**Success criterion:** an agent with working local EGL but broken child driver injection cannot show “Ready to stream” or proceed to an unexplained software-renderer failure.

### 5. Make setup show progress and prove the first stream

Reuse the existing readiness card in first-time setup and Fleet. Refresh it from provisioning events and bounded background checks; do not repeatedly stamp an old snapshot as fresh. Keep three questions distinct in user-facing text: is the agent connected, are host prerequisites ready, and has a stream been tested?

After host preparation, offer a short **Test this host** flow that launches a small known diagnostic app and verifies browser frame arrival, hardware rendering, input and audio. If it fails, show the failing stage and a bounded diagnostic bundle: for example, “App graphics initialized, but the browser received no video.” An agent-only boot check cannot prove router reachability or browser decoding.

Optional capability failures should remain warnings; required GPU prerequisites should prevent the affected launch while preserving administration. Use existing readiness statuses and summary/remediation fields wherever possible. A new scheduling promise or structured wire field needs separate contract review before implementation; this report does not amend frozen interfaces.

**Success criterion:** setup ends with a successful actual test or a named failing stage, rather than merely a healthy control-plane HTTP endpoint.

### What to build first

Prioritize three work packages. **First, repair the installation output:** one complete artifact, real dotenv values, stable secrets on rerun, working storage ownership, and image-set validation integrated with the ongoing release work. This removes avoidable manual intervention before the agent starts. **Second, make NVIDIA preparation and child graphics verifiable and recoverable:** restart-safe provisioning, fresh progress, verified mount identity and a child probe. This addresses the part that failed even after the compose was repaired. **Third, add the guided first-stream test and make that exact installation path a release gate.**

Do not begin by deleting the long environment list indiscriminately. First make defaults authoritative and prove the complete generated path; then remove duplicated default wiring from the basic artifact. Measure success by clean installs completed without edits, recovery after interrupted preparation, and successful app-to-browser streaming—not by the number of variables removed.

## Findings

The architectural concern is justified: the installation has independently maintained configuration producers, boot prerequisites hidden among tuning overrides, and several places where an agent-local observation is treated as evidence about the Docker host or a future app container. Correcting just six error messages would leave that failure class intact.

The smallest coherent response is: publish a tested, versioned installation bundle; make every installation front end consume it; establish image-local defaults before execution; validate host/agent/app boundary assumptions; and continuously report provisioning/readiness through the existing system. Identity preparation needs a small control-plane-specific entrypoint, not adoption of an app process supervisor.

Several issue claims need qualification:

| Claim in the issues | Verdict against the inspected evidence |
| --- | --- |
| Compose carries image facts. | **Holds for fixed paths/default wiring and duplicated detection flags.** It does not imply that most advanced overrides are illegitimate, or that devices, GPU requests and host mounts can be established by an entrypoint. The complete classification is in the [compose audit](2026-09-05-first-install-compose-audit.md). |
| Identity/ownership are assumed rather than adapted. | **Holds.** The image runs as uid 1000, while the generated bind mount relies on a separate shell step to prepare ownership. The script does that step; copying the compose does not. Arbitrary `user:` creates a second permission boundary at the private setup-token directory. |
| Nothing validates deployment before failure. | **Too absolute.** DB preflight, 13 readiness checks, an EGL child self-test, a bounded boot restart gate, image contracts, and installer checks already exist. They do not validate the complete install bundle or every cross-container prerequisite; readiness is advisory and stale. |
| All six failures are detectable inside the container at startup. | **False as stated.** An image that cannot be pulled never starts. Missing host devices can also prevent container creation. Publishing/installer validation is necessary before in-container preflight can help. |
| The wizard does not generate NVIDIA support. | **Not true of current source or the currently served bundle.** It generates a separate overlay and includes both files in its shell command. Its separately copyable base compose omits NVIDIA support. We do not have the original complete generated bundle or exact deployment invocation. |
| Log-level omission changed logging behavior. | **Not for default levels.** Both omitted levels default to `info`, matching the repo defaults; the provisioner skip is `debug` under both. Increasing required visibility at the source is the remedy. |
| `latest` never existed because CI is dispatch-only and only the default branch mints it. | **Current absence confirmed; historical “never” not provable from a tag list. Explanation incomplete/outdated.** The workflow also publishes on `v*` tag pushes and stable semver releases can mint `latest`. All three current runtime/updater packages still return 404 for `latest`. |
| Every killed provision leaves a 90-minute lock. | **True of the older implementation, not every current lock.** Current code has heartbeats and a five-minute minimum expiry; legacy locks retain 90 minutes. Expiry still requires another attempt; it is not an automatic retry. |
| #130 affects every host-networked agent. | **The risk is general, not universal.** Docker can give a host-networked container the host hostname, defeating that fallback, but mountinfo may still identify it correctly. A custom hostname can break the fallback on other network modes too. |

### Additional installer defects verified locally

1. **Own-certificate output does not parse.** `composeYaml()` indents conditional TLS environment/mount entries more deeply than their siblings. A generated Unraid/NVIDIA/self-signed file parsed successfully; changing only access to `own-cert` failed `docker compose ... config --quiet` with `mapping values are not allowed in this context` at line 34, column 24. No daemon was contacted. Existing 22 site tests all passed.
2. **Different certificate/key directories are not modeled.** `envFile()` mounts only the certificate directory, and maps both files into it by basename. A key selected under `/keys/` with a cert under `/certs/` cannot be reached even after indentation is repaired. Source: [stack-template.js:314](../../site/src/data/stack-template.js#L314).
3. **The separately copyable `.env` is actually a shell-expansion template.** It contains `$(openssl ...)` and `$(cd deploy && pwd)`. Docker Compose reads dotenv; it does not execute these shell commands. The script intentionally expands them in an unquoted heredoc, but the “individual files” UI offers that same template for direct writing. This affects credentials and updater stack-path resolution. The operator subsequently confirmed this was the confusing launch-path dependency they encountered and worked around by executing the commands manually. The exact original dotenv bytes are not available.
4. **Re-running the install script overwrites existing deployment secrets.** `cat > deploy/.env` generates a new DB password, enrollment token and encryption key without preserving old values. An existing Postgres volume keeps its original initialized credential; persisted encrypted secrets require the original key or configured previous key. Thus a plausible “run setup again” recovery can turn a partly working installation into authentication and decryption failures. Source: [scriptText](../../site/src/data/stack-template.js#L336), [secrets warning](../../control-plane/internal/secrets/store.go#L106). No script was executed against an installation.
5. **Database URL assembly is unescaped interpolation.** Both producers place a password directly into URI userinfo. Script-generated hex happens to be URI-safe; a manually supplied password need not be. Use structured connection parameters or correctly encode the URI component, and test hostile-to-serialization but legitimate password characters. Keep all error paths credential-free.

The hostname concern is supported by [Moby v27.1.1 container_operations.go:967](https://github.com/moby/moby/blob/v27.1.1/daemon/container_operations.go#L967): it assigns the host hostname for host networking when none is supplied. ## Boot preflight and reporting design

Reuse the existing readiness channel. [readiness.rs:309](../../node-agent/src/readiness.rs#L309) already checks NVIDIA EGL/vendor/lib32, visible render nodes, uinput, user namespaces, AppArmor, host render nodes, app uid access, driver version, encoder availability, Xid visibility and firewall posture. [agent.rs:456](../../node-agent/src/agent.rs#L456) already has bounded automatic restarts for selected boot faults. These are valuable foundations, not machinery to replace.

Readiness is computed once per **connection**, copied into the manager, and cloned into subsequent capacity reports ([agent.rs:999](../../node-agent/src/agent.rs#L999), [1654](../../node-agent/src/agent.rs#L1654)). A provisioning snapshot can therefore stay stuck at fail or provisioning, depending on timing; it is not guaranteed to be captured before work starts. The control plane stamps receipt time again on each report ([store.go:433](../../control-plane/internal/agentws/store.go#L433)), so the UI's recent timestamp can accompany an old observation. That is worse than merely missing a progress bar.

Both [ReadinessCard](../../web/src/components/ReadinessCard.tsx#L23) and [setup StepHosts](../../web/src/pages/setup/StepHosts.tsx#L213) already exist and understand provisioning. Setup explicitly tells users to restart to refresh. Feed fresh results into both rather than creating a parallel install-status service. Progress can use the existing status plus summary text; dedicated structured progress fields would require a separately reviewed contract change.

| Boundary | Check and necessary access | Surface and response |
| --- | --- | --- |
| Before container creation | Compose syntax/version support, image manifests for the whole bundle, required host devices, chosen bind sources, toolkit availability, consistent rendered secrets. Registry access and installer host access. | Installer/Unraid import diagnostics and publishing gate. Cannot rely on the unstarted CP UI. |
| CP before serving | Parse/connect DB; state read/write/rename and private token creation as final uid; certificate/key readability; persisted encryption-key continuity; updater socket accessibility. Only configured CP mounts/DB needed. | One cause-specific startup error per failed prerequisite, credential-redacted. Ownership wrapper prepares only intended directories, then execs Go as non-root. |
| Agent boot | Docker daemon access and self identity; network mode; mount source/destination mapping for runtime/home/template/driver; selected GPU identity; actual device access; persistent volume writability/free space; provisioning manifest/trust/lock state. Docker socket, configured binds, sysfs/proc already cover much of this. | Existing host readiness, fresh during changes. Required unresolved paths should stop affected app launches with an explicit cause, while preserving the management connection. |
| Provisioning | Async phase/progress/failure events; restart safety; lock owner/lease or kernel lock; bounded retry on recoverable errors. Volume plus network. | `provisioning` with no manual repair advice; failures name lock/download/disk/integrity cause. A dead process must not require operator lock deletion. |
| Before first launch / after changed prerequisites | Bounded probe using actual app image, uid/groups, devices and driver mounts; validate hardware renderer and loader compatibility, and shared sockets. Requires temporary child container. | This is recommended **future validation**, not executed during this investigation. Cache only against image digest, driver version, GPU, identity and mount configuration; don't reuse across changes. |
| First stream | Browser decode, media transport, input, audio, and actual app renderer. | Explicit acceptance test. A healthy API or agent-side encoder probe cannot establish a working stream. |

A periodic full GPU probe on the heartbeat thread would be a regression: the code already offloads blocking probes. Prefer event-driven cheap updates while provisioning, bounded background rechecks, and invalidation after relevant settings change. Do not repeatedly restart a healthy session to repair an unrelated optional feature. Classify required GPU prerequisites separately from optional warm-up/Xid observability.

Current readiness is documented as advisory; making the **scheduler** depend on it or changing wire statuses/fields is a contract-sensitive design decision. It is possible to improve messages, refresh existing reports and reject impossible realization locally without altering `protocol/`. Stop at design review for any new frozen shape or scheduling promise. This pass makes no such change.
