## #824 Release detection: verify the manifest signature when trusted keys are configured

**Changed:** on an owned install, detection asks the control plane's recovery actor to verify each new stable release's `.sig` over the fetched manifest (control socket `POST /v1/verify-manifest`); a refused or unanswered check keeps the release out of the list and counts it in the run's `manifest_errors`. Mode `off`, no actor, or an actor older than the route: unchanged.
**Rows:** on amd-test (owned install on the integration image), after 0.6.5 ships: (1) delete the stored stable rows newer than the installed release (`DELETE FROM platform_releases WHERE channel='stable' AND version > '<installed>'`), Fleet ▸ Releases "Check now": the signed releases come back, the run in Fleet ▸ Jobs shows `manifest_invalid: 0`. (2) `quasar-recovery reconfigure --yes QUASAR_UPDATER_TRUSTED_KEYS=other:<any other 32-byte key>`, delete the rows again, "Check now": none come back, the run shows `manifest_invalid` = their count and `manifest_errors` naming `signature refused by the recovery actor`, the control plane logs `platform release manifest rejected`. (3) `reconfigure --yes QUASAR_UPDATER_SIGNATURE_MODE=off`, "Check now": they come back. Reset trust (`reconfigure` back to the recorded values) afterwards.
**Pass:** with keys configured, a release that does not verify is not listed and the refusal shows in the Jobs run summary and the log; off lists as before.
**Hosts:** amd-test (no GPU path involved; one host is enough).
