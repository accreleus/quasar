# Issue tracker: GitHub

Issues and specs for this repo live as GitHub issues on **`accreleus/quasar`**. Use the `gh` CLI for all operations.

Referenced from `CLAUDE.md` → "Agent skills". This file is the durable answer to "where do issues live and how do I touch them", so a session never has to infer it from `gh label list`.

## Conventions

- **Create an issue**: `gh issue create --title "..." --body-file <file>`. Prefer `--body-file` with a heredoc over `--body` for anything multi-line — the bodies here carry fenced code, tables and backticks, and shell quoting mangles them.
- **Read an issue**: `gh issue view <number> --comments`
- **List issues**: `gh issue list --state open --json number,title,body,labels,comments --jq '[.[] | {number, title, body, labels: [.labels[].name], comments: [.comments[].body]}]'`, with `--label` / `--state` filters as needed.
- **Comment**: `gh issue comment <number> --body-file <file>`
- **Apply / remove labels**: `gh issue edit <number> --add-label "..."` / `--remove-label "..."`
- **Close**: `gh issue close <number> --comment "..."`

`gh` infers the repo from `git remote -v` when run inside a clone. **In a git worktree this still works, but `gh issue edit --body-file` can fail with `fatal: not a git repository` if the CWD is outside the repo** — run `gh` from the repo (or worktree) root.

## Issue body conventions

The house style is **not** the generic agent-brief template. Existing issues (#67, #80, #82, #83, #85, #86) use, in order:

```markdown
## Symptom          — what the operator sees, with the reproducing conditions
## Root cause       — the mechanism, citing `path/to/file.ext:line`
## Suggested fix    — direction, not prescription
## Acceptance       — concrete, checkable
## Related          — sibling issues, with the relationship stated
```

Unlike the generic advice in the `triage` skill's `AGENT-BRIEF.md`, **this repo does cite file paths and line numbers**. They go stale, and that is accepted: the tree moves fast enough that a precise-but-aging pointer beats a vague-but-durable one. Keep the surrounding prose descriptive enough to survive the pointer rotting.

## Wayfinding operations

Used by `/wayfinder`. The **map** is a single issue with **child** issues as tickets.

- **Map**: an issue labelled `wayfinder:map` holding the Notes / Decisions-so-far / Fog body.
- **Child ticket**: an issue linked to the map as a GitHub sub-issue (`gh api` sub-issues endpoint). Where sub-issues aren't enabled, add the child to a task list in the map body and put `Part of #<map>` at the top of the child body. Labels: `wayfinder:<type>` (`research` / `prototype` / `grilling` / `task`).
- **Blocking**: GitHub's native issue dependencies. Add an edge with `gh api --method POST repos/accreleus/quasar/issues/<child>/dependencies/blocked_by -F issue_id=<blocker-db-id>`, where `<blocker-db-id>` is the blocker's numeric **database id** (`gh api repos/accreleus/quasar/issues/<n> --jq .id`, *not* the `#number` or `node_id`). Fall back to a `Blocked by: #<n>` line in the body where dependencies aren't available.
- **Frontier query**: the map's open children, minus any with an open blocker or an assignee; first in map order wins.
- **Claim**: `gh issue edit <n> --add-assignee @me`.
- **Resolve**: comment the answer, close, then append a context pointer to the map's Decisions-so-far.

## Note on `wontfix`

The repo carries GitHub's stock `wontfix` label. Per the `triage` skill, a rejected **enhancement** also gets a note written to `.out-of-scope/` and linked from the closing comment; a rejected **bug** just gets a polite explanation. An *already implemented* request is closed pointing at the implementation and does **not** get an `.out-of-scope/` entry.
