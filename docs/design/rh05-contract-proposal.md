# RH05-01 contract proposal for review

Status: **proposed, not approved**. Issue [#334](https://github.com/accreleus/quasar/issues/334); specification [#333](https://github.com/accreleus/quasar/issues/333). Baseline: Quasar `f10a8a1725d70548febd7f3748b7c5afe0662188`, protocol `f7a08e3c77a01837ad606ee022654764c887aa6f`, schema migration 0086. This document is the review packet for amendments to `agent-api.md`, `control-api.md`, `schema.md`, and `openapi.yaml` in `quasar-protocol`. It changes no frozen contract or production behavior.

## Interface ownership and terms

The control plane owns desired policy, operator revisions, app placement, admission restrictions and scheduling. The authenticated agent owns accessible-device discovery, application evidence, durable local configuration attempts and recovery. The existing image Ensurer remains the only managed-image executor. Platform-image replacement remains with the updater. `Configuration applied` means verified for its declared scope; `app prepared` means local image and required preparation complete; readiness remains its own evidence-based verdict. None implies the others.

Use `source=automatic|deployment|explicit` for each supported knob. `deployment` means the agent's **existing** baseline resolution, including environment variables, legacy device detection and per-key fallback. The control plane's catalog default is a display fallback and must not override that agent resolution; in particular, an unset encoder can still take the agent's existing GPU-detection path. An explicit value has the catalog type. Automatic is a deliberate choice and requires a supported resolver and current accessible-device evidence. A legacy PATCH `{"overrides":{"gop":null}}` removes the override and selects **deployment**, never automatic. Omitted keys are unchanged. `resolved` in the old GET remains its legacy display projection; the new typed status supplies real provenance, and neither projection by itself proves application. The old prose saying null can be retained as an explicit null or always restores a catalog default must be corrected to match the sparse override implementation and #194 precedence.

### Setting/source/effect/evidence matrix

`D/E` = deployment or explicit; `A/D/E` additionally permits automatic. `N` = next session, preserving existing sessions; `R` = approved agent restart after idle. `V` = authenticated, revision and content-bound agent effective readback at the declared scope; `P` = accessible-device inventory plus successful relevant host probe; `S` = startup readback and verification after the approved restart. Each ordinary `N` row is an independent atomic group unless cross-key validation links it to another row. Numeric bounds are inclusive. All explicit values must retain `hostcfg.Catalog` validation; boolean rows require a JSON boolean and integer rows a JSON integer. This is a freeze of the current catalog, not a new tuning policy.

Automatic `encoder` and `render_node` resolve as **one hardware group** using existing encoder preference, accessible device nodes and the real media host probe. An ambiguous or failed probe leaves this group pending with a remedy; it never falls through to a guessed vendor path. The hardware group includes `cuda_device` when explicitly set, because the selected encoder/device combination must validate together. Existing NVIDIA library discovery is preserved but RH05 introduces no automatic source for its path. No automatic numeric performance, ABR, GOP, queue, storage mount or concurrency tuning is introduced. `home_root` stays within the existing mount and must not relocate a claimed home. Console configuration retains its separate existing contract; a local-session-disruptive change is classified `R` before any RH05 idle apply can carry it.

## Proposed additive operator and agent contract

Add a typed settings view and CAS edit beside the legacy GET/PATCH, retaining old shapes for mixed fleets. Proposed `GET /v1/admin/hosts/{id}/policy` returns `revision`, choices, resolved values with source and evidence time, per-group `desired_revision`, `applied_revision`, `scope`, `status` (`pending|applied|failed|upgrade_required|uncertain`), freshness and remedy, plus separate image preparation and readiness views. `PATCH` accepts `{expected_revision,changes}`; the whole request validates before any persistence. A mismatch is `409 stale_revision` with current view and changed keys, not last-writer-wins. A valid edit commits choices, monotone revision and reconciliation obligation in one transaction. Offline save returns pending. `POST .../idle-apply` accepts reviewed group fingerprint and prerequisites; `POST .../idle-apply/{attempt}/cancel` and `POST .../retry` have stable attempt IDs. Admin authorization applies server-side to every operator mutation. Legacy PATCH without a revision remains a compatibility exception: it serializes under the host settings row and increments the same revision, but cannot detect a stale client's snapshot. New clients must use CAS. A legacy non-null write sets that key to explicit; null selects deployment, including when the prior source was automatic. Both supersede an unstarted approval if relevant.

Add `register.rh05_capabilities` with explicit versions for typed settings, execution journal, idle apply and preparation observation. Missing capabilities mean legacy agent. The control plane chooses **one configuration writer per connection**: legacy sparse `config_update` for supported legacy knobs, or the RH05 command set; it never sends both to race. New commands carry `attempt_id`, host ID, control-plane boot incarnation, authenticated connection incarnation, resource/group revision, canonical content digest, scope, prerequisites and expiry. The agent rejects a grant from any prior connection/boot, wrong host, mismatched content, unsupported capability or changed prerequisite. New agent result messages carry the same identity tuple and a monotone attempt phase; the control plane accepts them only from the authenticated host's current connection and matching durable attempt. A legacy `capacity.effective_settings` map remains informational, never RH05 application proof.

Agent phases are `offered → accepted → activating → verifying → applied|failed|recovery_verifying|recovered|uncertain`. **Execution starts exactly when the agent has fsynced an `accepted` record with attempt ID, approved digest, candidate and last verified snapshot to its local journal and atomically published that record before any restart or activation.** The control plane persists `started` only after the agent reports that durable acceptance, but loss of that report does not reauthorize dispatch: reconciliation obtains the agent's complete authenticated journal inventory, including attempts absent from the current database, before it permits scheduling. Such an orphan is reconstructed only when its durable identity/content can be matched to surviving policy; otherwise it is quarantined and its host remains restricted for operator repair. The report's historical boot/connection IDs identify the original grant; the current authenticated connection authorizes the inventory report. Duplicate delivery returns the recorded phase/result; a different digest with the same attempt ID is rejected. Receipt, socket send, ack, candidate validation and pre-startup effective maps are not application evidence. Next-session `applied` requires the agent's active next-session snapshot and revision/digest readback; restart `applied` requires post-restart startup proof for the requested group. Reports for an older revision cannot advance a newer group. A report for group A does not advance B.

Errors are typed: `validation_failed` (400), `stale_revision` (409 plus current/diff), `unsupported_source` (400), `upgrade_required` (saved valid intent, pending), `approval_superseded` (409), `approval_expired` (409), `host_busy` (pending, not a forced stop), `attempt_conflict` (409), `cancel_too_late` (409 with current attempt), `retry_exhausted` (visible terminal failure), `home_conflict` (launch refusal without another user's data), `placement_ineligible` (launch refusal), and `recovery_uncertain` (protective admission hold). Transport failures are pending with bounded exponential backoff and a recorded next retry; exhausted attempts retain intent and require explicit Retry or a relevant condition change. Validation errors are never retried. A retry of a disruptive group needs fresh, scoped approval.

Proposed representative wire shape for review (names freeze only in the signed protocol amendment):

```json
{"type":"rh05_config_offer","attempt_id":"<uuid>","host_id":"<uuid>","boot_incarnation":"<uuid>","connection_incarnation":"<uuid>","group":"hardware","revision":12,"content_sha256":"<64 lowercase hex>","scope":"restart","expires_at":"2026-09-23T09:00:00Z","prerequisites_sha256":"<64 lowercase hex>","settings":{"encoder":{"source":"automatic"},"render_node":{"source":"automatic"}}}
```

```json
{"type":"rh05_config_state","attempt_id":"<uuid>","grant_boot_incarnation":"<uuid>","grant_connection_incarnation":"<uuid>","revision":12,"content_sha256":"<64 lowercase hex>","phase":"accepted","journal_sequence":4,"active_scope":null,"evidence":null}
```

`accepted` acknowledges durable execution start, not application. A later `applied` state supplies `active_scope`, verified values, agent process identity, observation time and evidence IDs. The authenticated WebSocket connection, never the JSON `host_id` alone, establishes which host may report a journal inventory. Inventory is paginated or bounded by a required continuation cursor so older attempts cannot be silently omitted. A journal sequence must strictly increase for a given attempt; duplicate sequence with identical content is idempotent, and conflicting content is an error. Capabilities are an explicit versioned object on registration; absence selects legacy behavior.

## Idle apply, recovery and restore

Approval binds the reviewed disruptive group, resolved content digest and evidence/prerequisite identities, and the current control-plane boot incarnation. A safe edit outside that group preserves approval; an edit to its source, resolved value or prerequisite invalidates an unstarted approval. Every control-plane restart changes incarnation and expires **all unstarted** approvals before dispatch resumes; saved choices survive. A stopped-stack database restore is the supported restore procedure and necessarily starts a new incarnation. An unsupported live database rewind is outside the guarantee. Connection-bound grants expire on agent reconnect; a started attempt is discovered by full journal inventory, not replayed from an old approval row. After restart or restore, admission stays protected until inventory/restriction reconciliation is complete; a database backup may predate an agent-accepted attempt and omit both its attempt row and restriction.

The idle operation acquires an owner-scoped restriction atomically with the attempt. It waits for zero assigned, starting, running and stopping sessions, including local sessions, and for conflicting preparation to finish or confirm cancellation/cleanup. Missing inventory is uncertainty, never zero. A final agent-side check occurs under the same launch exclusion before durable acceptance. Waiting has no deadline that kills sessions. Cancellation or relevant supersession first fences further grants in the database, then sends revocation for any offered grant. The agent serializes revocation and durable acceptance under one journal lock: it returns either `revoked_unstarted` or `accepted`. A lost response keeps cancellation pending and admission restricted until fresh journal inventory proves which occurred. Only confirmed nonacceptance removes this operation's restriction before execution; after acceptance it waits for a safe terminal/recovery point. Manual and platform restrictions remain. An uncertain started attempt retains its own restriction until verified reconciliation or explicit repair.

Before activation the agent durably stores a validated candidate and the last verified configuration. Failure retains the original attempt as failed and permits **one** recovery activation of that exact last verified group when safe, followed by fresh verification. Successful recovery reports `recovered` alongside the original failure and releases only the idle operation's hold; it does not mark the requested choice applied. Failure or uncertainty during recovery retains protective admission. New unrelated safe changes are kept separate and re-reconciled later. No configuration recovery replaces a platform image, repairs a broken binary/runtime/mount, or overrides the updater's authority (ADRs 0002 and 0004).

## Schema and migration reservation

Reserve **0087–0093** for RH05 on this initiative branch, conditional on rechecking `origin/develop` immediately before authoring each migration. One owner writes each: #335 owns 0087 (typed settings, revisions, per-group observations and obligations); #337 owns 0088 (owner-scoped admission restrictions, legacy cordon backfill); #338 owns 0089 (approval/attempt ledger and boot-incarnation metadata); #341 owns 0090 (canonical home claim); #342 owns 0091 (canonical app placement); #343 owns 0092 (per-host prior successfully prepared managed-image version); #345 owns 0093 (image operation fence). #344 consumes the prepared-image schema without inventing another writer. No worker may create a migration with another worker's ID. If upstream consumes an ID, renumber the entire reservation before any shared migration is pushed; never ship duplicate numbers.

0087 keeps `host_settings.overrides` for legacy compatibility and backfills each present non-null override as explicit. An absent or legacy cleared override becomes deployment; existing hosts are **never** backfilled to automatic based on a catalog or installer default. New hosts may initialize supported keys to automatic only after enrollment/capability evidence. Unknown historical intent remains deployment. Legacy PATCH runs through the same CAS write path, preserving null-clear and incrementing revision; it must not bypass RH05 state. 0088 records existing manual/legacy cordons as a distinct owner, never treats `hosts.status` as an owner token to clear globally. 0090 places all existing canonical apps in dynamic all-eligible mode so current scheduling remains eligible; derived tiles have no separate placement row. Backfill home claims from known `user_homes` locations. Multiple or ambiguous legacy locations become explicit conflicts, not invented ownership. 0091 seeds retained prior version only from a **verified** successful prior preparation record; unknown history stays unknown and cleanup fails closed for uncertain references.

Each up migration is additive and has a corresponding down migration that removes only its new structures. Rolling down after an RH05 operation loses policy/attempt/claim/retention evidence and is therefore **not** a safe live rollback; export/reconcile first and use a schema-compatible binary. No down migration may delete existing `user_homes`, images or session rows. `host_settings.overrides`, `hosts.status`, existing platform run records and `host_images` remain in place during mixed-version transition.

Transaction order extends the existing scheduler's order: per-user advisory lock (namespace 1) → canonical parent app row `FOR SHARE` → entitlement `FOR SHARE` → per-GPU advisory lock (namespace 2) → selected host row then GPU row → admission restriction decision → placement row `FOR SHARE` → managed home claim keyed by user and canonical parent → session reservation. App deletion already locks the app before cascading entitlements, so the new early app lock prevents entitlement/app deadlock; verify this against delete and launch in Postgres. A restriction writer locks the host row and writes only its own restriction, never takes a user/GPU lock afterward. Placement writers lock app then placement and never acquire a host lock afterward; a workflow needing both must split transactions or follow the launch order. A first claim inserts under the unique key and retries on conflict before assigning, so two launches cannot choose different hosts. A failed launch releases a claim only if it created an unmaterialized reservation and authoritative host evidence confirms no home exists. A materialized or uncertain claim persists. Placement removal and reservation lock the same placement row. Swap and local-launch paths must apply the same canonical placement and home-claim check before changing executable app identity; no alternate path may create a second home. Unknown or divergent legacy locations are represented as a conflict with no chosen host until repaired.

For image cleanup, a database `host_image_operation_fences` row serializes every requirement-changing placement/adoption transaction, launch reservation and cleanup decision for that `(host,image)`; writers increment its generation. Cleanup first enters `removing` with a generation token while rechecking the union of selected app requirements, all container references, pending ensure/template operations and retained prior successful version. The agent takes its local per-image operation lock and rechecks local container/template references and the current fence token before physical removal. A new requirement racing an active removal cannot be reported ready: it either cancels an unstarted removal under the fence or remains pending and triggers re-ensure after removal. Launch admission refuses the image until the required version is verified ready again. Stale preview or unknown inventory never authorizes deletion. No database transaction stays open across network, process restart, image pull or physical removal. Existing platform cordon writers must migrate to owner-scoped acquisition and release before the old boolean is retired. Integration order for reserved migrations is 0087 before 0088 before later numbers, even if #335 and #337 implement in parallel; never deploy an 0088-only branch to a shared database.

## Executable conformance examples to add after amendment approval

These examples are intended as black-box fixtures at operator status/action, session launch and image/preparation interfaces. JSON values are illustrative; frozen names are finalized in protocol review.

1. **Legacy clear:** an unset encoder environment on a GPU host resolves via the agent's existing detection to `nvenc`; explicit `encoder=va` is then cleared by legacy PATCH null. Status source is deployment and effective value is `nvenc` after evidence. It never selects automatic or catalog `openh264`.
2. **Old agent:** an old agent accepts a supported legacy `gop` update, but no RH05 proof exists. Status shows legacy observation/unknown application; a requested automatic encoder or idle apply shows upgrade required and cannot read applied.
3. **Concurrent edit:** two admins read revision 7. First saves `gop=90` at 7 → 8. Second saves `slices=4` at 7 → 409 with current revision 8 and `gop` change; neither the second choice nor obligation is committed.
4. **Independent work:** selected app image pull fails while next-session `gop=90` proves applied. Config is applied, app preparation failed and readiness remains separately evaluated; the image error never rolls back `gop`.
5. **Offline and reorder:** save revision 11 while host is offline, then 12. On reconnect only 12 is authority; an old 11 observation and a duplicate 12 command cannot advance or repeat work. A valid 12 evidence report advances only its matching group.
6. **Approval scope:** approval for hardware digest H survives unrelated `gop` edit, but a `render_node` edit or changed accessible-device identity supersedes it. A stale grant is rejected. A new boot incarnation expires any unstarted approval; a journal-accepted attempt is reconciled.
7. **Restore and crash:** stop stack, restore a database containing waiting approval, restart control plane. The approval expires before dispatch and settings remain. If the agent journal records acceptance before the backup, authenticated full inventory discovers the attempt even when the restored database has no row; the host stays restricted until matched/reconstructed or quarantined. The same attempt is completed at most once; uncertainty retains admission protection.
8. **Admission overlap:** manual, platform and idle operation each hold the host. Idle cancellation deletes only idle's row; manual and platform still exclude it. Scheduling that races acquisition observes one serial order and cannot reserve after the idle hold wins.
9. **Home and image races:** two simultaneous first launches for the same user/canonical app choose one home host; a conflicting known legacy location refuses launch. Placement removal racing reservation yields either an earlier valid reservation or refusal, never a new reservation after removal. Cleanup racing a committed shared app requirement, container or template reference retains the image; a new requirement arriving during an active removal waits for verified re-ensure before launch.
11. **Delayed grant and cancellation:** a grant is sent, then cancellation fences dispatch and its revocation reply is lost. The operator sees cancellation pending and the host remains restricted until agent inventory proves `revoked_unstarted` or `accepted`; a delayed grant cannot start after an acknowledged revocation.
10. **Steam:** a new empty home seeds from an exact compatible template by reflink if available, else full copy, else cold launch; status names the actual path. An existing home is byte-preserved and is never retrofitted. Copy and cold paths claim no reflink storage saving.
