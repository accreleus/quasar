## 1. The question

#207 says: "Explicit single-writer ownership for CP, host agent, Postgres and TURN. A
restart policy is not an image updater. Remove Compose-dependent updating only after a
recoverable replacement and installation migration exist." #218 asks for versioned service
specs, a persisted phase journal and independent control-plane replacement/recovery
authority. #219 asks for minted-token bootstrap, opt-in adoption of existing stacks that
preserves identity, homes, volumes and secrets, and an end state where "managed updates no
longer read/write manager .env or depend on Compose labels/paths".

To shape that, we need to know exactly who owns what today, and where the ownership leaks
into a Compose project or an external manager's files.

## 2. What is deployed, and by whom

### 2.1 Services and host shapes

- [F] The base `deploy/docker-compose.yml` **is** the production deployment. It has four
  services: `quasar-postgres`, `quasar-control-plane` (it carries the SPA; there is no web
  service), `quasar-node-agent`, `quasar-updater`. There is no TURN service. Every service
  is `restart: unless-stopped`. (b §1)
- [F] Supported shapes: the **combined host** (all four services), and an **additional GPU
  host** installed by `deploy/enroll-host.sh` (agent + updater only, project `quasar-agent`,
  files under `/opt/quasar-agent/`). (b §1)
- [F] **There is no supported control-only host.** The only agentless compose file is the
  contributor overlay `deploy/overlays/docker-compose.local.yml`. #218 asks for one. (b §1)
- [F] The combined-host agent reaches the control plane at `ws://localhost:${CONTROL_PORT}`
  over the host network (`deploy/docker-compose.yml:325`). (b §1)
- [F] Postgres is reached by Compose service DNS (`quasar-postgres`) with the password
  interpolated from `.env`. `DATABASE_URL` or `QUASAR_DATABASE_*` can already point the
  control plane elsewhere, but no shipped file shows it. (b §1, §7)

### 2.2 Four install origins, one shared convention

- [F] (A) registry install from the base file, (B) `deploy/redeploy.sh` from a source
  checkout (project `deploy`, dev overlay always appended), (C) `deploy/enroll-host.sh` for
  extra GPU hosts, (D) the public site installer (`site/src/data/stack-template.js`), which
  generates one compose file, uses the split `QUASAR_DATABASE_*` variables and `control.env`
  / `agent.env` side files, and refuses to take over a stack whose `working_dir` label
  differs. Each writes `.env` slightly differently. (b §1)
- [F] Unraid appears only as a platform choice inside the site installer (persistent
  appdata path, `/boot/config/go`, uid 99:100). There is **no Unraid Community Applications
  template, and no Portainer, Dockge, TrueNAS, CasaOS or Synology integration** anywhere in
  the repo. (a §3, b §1)
- [I] An RH-06 migration therefore has at least four origins to recognise, and none of them
  records which origin it was.

### 2.3 Who writes what today

| Actor | Owns / writes | Mechanism |
|---|---|---|
| Operator or an external manager | the compose files, the overlay chain, `.env` | by hand, installer, or manager UI |
| `redeploy.sh`, `enroll-host.sh`, site installer | `.env` (secrets, image pins, `QUASAR_STACK_DIR`, project name) | shell, on install or re-run |
| Updater | two lines of `.env` (`QUASAR_CONTROL_IMAGE`, `QUASAR_AGENT_IMAGE`), `.env.prev`, result files | `docker compose pull` + `up -d --force-recreate --no-deps --wait` |
| Control plane | Postgres (everything durable), the apply state machines | never touches a container |
| Node agent | session, audio and probe siblings (RH-01 owner label); its own journal files | Engine API; restarts itself only by exiting |
| Restart policy | brings every service back after exit | Docker |

- [I] **No single writer owns `.env`.** The operator, three installers and the updater all
  write it; re-running `enroll-host.sh` replaces an updater-applied agent pin. (a §3)

  (Portainer or Dockge "stacks") does set the labels, but its working directory and file
  paths are the manager's internal paths; the updater would need them mounted at identical
  paths and would then edit the manager's `.env` behind its back, and the manager may later
  rewrite that file from its own stored copy. Nothing in the repo has tested either case.

## 4. Behaviour today, by concern

### 4.1 Control-plane update

- [F] A platform release is exactly two components, `control-plane` then `node-agent`,
  pinned by digest in `platform-release-manifest.json` (ADR 0001). Detection is the weekly
  `platform.release_detect` job; `PlanRelease` is a pure decision (ADR 0002 ordering by
  schema version, downgrade unrepresentable). (a §1.2-1.3)
- [F] **The control plane moves only inside a fleet run**; there is no standalone
  control-plane apply endpoint. (a §1.5)
- [F] It applies itself through the local updater socket, never through an agent. It
  persists `updater_request_id` before the call, then polls until it is killed by its own
  recreate. **Success is its own next boot reporting the release's commit** (`Adopt`).
  (a §1.7)
- [F] A non-migrating control-plane step rides live sessions through (agent holds them for
  a 90 s grace; the control plane's stale sweep uses 120 s). A migrating step drains the
  whole fleet first; unattended apply refuses a migrating release twice. (a §1.6, §7)

### 4.2 Node-agent update

- [F] The control plane sends `release_apply` over the agent WebSocket; the agent validates
  it (only `node-agent` is appliable by an agent, a confused-deputy guard), POSTs to its
  local updater, and relays the result file as `release_state`. **Success is the new agent's
  `register` carrying the release's `source_commit`.** (a §7)
- [F] Recreating the agent ends every session on that host; the new agent's startup sweep
  removes the old siblings. Draining is the control plane's job via owned admission
  restrictions. (a §7)
- [F] The agent has **no authority over any platform container, its own included**. It
  reads its own container (labels, mounts, image), runs its own image for Pulse and probes,
  and restarts itself only by exiting. (b §5)

### 4.3 Failed health checks and automatic restore

- [F] The updater judges the post-state, not compose's exit code: running + healthy (or no
  healthcheck) passes; `StartedAt` zero is `never_started`; otherwise `recreate_failed` or
  `unhealthy`. (a §2.6)
- [F] ADR 0004: a failed **agent** apply is restored by the updater (`.env.prev` back, `up`
  again, no pull), reported `restored: true`, and recorded as an `auto_revert` attempt; the
  run still stops. A **control plane** is restored automatically only if it never started,
  because a started one may have migrated. `pull_failed` restores `.env` only. (a §1.8)
- [I] The restore re-runs `up` without a pull, so it depends on the previous image still
  being in the local store; an image prune in between makes it fail. (a §2 inferences)

### 4.4 Rollback and revert

- [F] ADR 0002: revert exists only for agents, only to the control plane's release or
  older, and never offers the release that just failed (`auto_revert` rows are skipped).
  The control plane is never revertible. (a §1.8)
- [F] Revert is a `release_apply` carried by the host's own agent, so it cannot help an
  agent that will not start; that is why ADR 0004 moved the restore into the updater. (ADR 0004)

### 4.5 Interrupted pull / create / replace / health check

- [F] **Control-plane side is durable.** Runs, attempts, request ids and cordons are in
  Postgres; `Close` leaves rows non-terminal on purpose; boot re-adopts (`applyRunner.Adopt`
  → `ResumeCordonRestores` → `fleetRunner.Adopt`). The deadline is 15 min from `started_at`.
  (a §1.10)
- [F] **Updater side is not.** Its single-flight latch and accepted-request cache are in
  memory only (`internal/updater/result.go:53-62`); `NewStore` does not scan existing result
  files and `main` has no recovery step (`result.go:74-83`, `cmd/quasar-updater/main.go:103-151`);
  `docker compose` runs as a child process (`exec.go:31-51`); `.env.prev` and `.env` are
  written with plain `os.WriteFile` (`exec.go:86-95`). *(Verified by hand for this document.)*
- [I] So if the updater is stopped or killed mid-apply: the compose child dies with it; the
  result file stays at `pulling`/`recreating`/`verifying` for ever; `.env` may already name
  the new digest while the old container runs; and a second apply would overwrite
  `.env.prev` with the already-rewritten `.env`, losing the original pin. The agent poller
  keeps re-reading the stale file until its 2 h deadline. This contradicts
  `docs/upgrading.md:401-403` ("an apply in flight is a detached `docker compose`
  invocation that finishes regardless"). A power loss mid-write can truncate the
  operator's `.env`, which also holds the database password and secret key. **Not yet
  demonstrated by a test.**
- [I] `up` re-reads the current compose files, so a recreate also applies any drift in the
  service definition since it was created. The `updater_overlays` preflight compares the
  `-f` list, not file contents.

### 4.6 Database migrations, backups, restores

- [F] Boot: DB preflight → golang-migrate `m.Up()` → pool → services. A DB newer than the
  binary is a named, translated error; a dirty DB is passed through untranslated. A release
  "carries a migration" iff `release.schema_version > control-plane schema_version`
  (`ReleaseRunsAMigration`). (a §6)
- [F] **No automatic backup exists anywhere in the update path.** `pg_dump` appears only in
  `deploy/db-backup-restore-drill.sh` and one DB test. Backup and restore are a manual,
  documented procedure (`docs/upgrading.md` "Back up Postgres…";
  `docs/operations/database-backup-restore.md`: "Never restore over a live database"). The
  upgrade-from-last-supported rehearsal is SKIP/blocked for want of a supported-pair
  manifest. (a §6)
- [F] RH-05's contract: "A supported database restore stops the stack first and starts a
  new boot incarnation; a live rewind has no guarantee" (`protocol/agent-api.md` §"Durable
  start, restart recovery, and database restore"); ADR 0006 expires unstarted approvals on
  every boot so a restore cannot replay one. (c §8)
- [I] A migration that fails part-way leaves `schema_migrations` dirty; the new control
  plane crash-loops under the restart policy, the updater sees a started container and does
  not restore it, and the old binary cannot start if any migration committed. Recovery is
  manual, and nothing took the dump it needs.
- [I] A migration longer than the compose `--wait-timeout` (300 s default) is reported
  `unhealthy` even if it later succeeds. Which record wins, the updater's `failed` or the
  next boot's commit match, is not established.

### 4.7 Enrollment and identity

- [F] **A host's identity is `node_name` plus `node_secret`, nothing else**: no machine id,
  keypair or client certificate. `hosts.node_name` is `UNIQUE`; the secret's SHA-256 is
  stored. The agent's only certificate involvement is pinning the control plane's TLS leaf.
  (b §2)
- [F] The agent keeps six files beside `NODE_SECRET_PATH` on the `quasar-agent-data`
  volume: the secret, `.tls` (control-plane pin), `.images.json`, `.policy.json` (RH-05
  journal), `.runtime-images`, `.container-owner` (RH-01 ownership lease). (b §2)
- [F] Enrollment string `qenr1.<FP>.<base64url(wss-url)>.<token>`. Minted tokens (#12/#96,
  table `host_enrollments`) are 32 random bytes stored hashed, default single use and one
  hour, optional `node_name` binding, `max_uses` 1-100, expiry up to 30 days, revocable
  through the admin API. The console always mints any-node, single-use, one-hour tokens and
  has **no list or revoke UI**. (b §2)
- [F] The static `ENROLLMENT_TOKEN` is optional to the control plane but **required by the
  base compose file**, so every combined host carries a break-glass "enroll any node name"
  credential. (b §1, §2)
- [F] Enrollment onto a live `node_name` is refused (#96). Re-enrollment with the same name
  re-keys the row; a changed name creates a new row and orphans the old one; a secret from
  a different or restored control plane falls back once to the configured token (#199).
  (b §2)
- [F] `register` carries optional `source_commit`, `built_at`, `install_mode`
  (`registry|source`), `updater_present`; a host with any of them NULL is never eligible for
  an apply. (b §2; `protocol/agent-api.md`)
- [I] Because the identity volume is named `<project>_quasar-agent-data`, moving a host to a
  different manager or project name silently loses its identity, its RH-01 ownership lease
  and its RH-05 journal unless the volume is carried over. Losing `.container-owner` turns
  surviving session containers "foreign" (preserved, never retired).

### 4.8 Secrets

- [F] Irreplaceable, and held **only** in the stack's `.env`: `POSTGRES_PASSWORD` (Postgres
  ignores a new one once initialised), `QUASAR_SECRET_KEY` (+`_PREVIOUS`; without it every
  `instance_secrets` value is unrecoverable). The control-plane TLS pair lives in the
  `quasar-control-tls` volume; re-issuing it changes the fingerprint and disconnects every
  pinned remote agent until each is given the new one. (b §3)
- [F] There is no JWT or session-signing key (tokens are stored hashed) and no registry
  credential (GHCR is anonymous; private registries are #9). (b §3)
- [I] If managed updates stop reading or writing the manager's `.env` (#219), these secrets
  need either a new durable home or an explicit rule that they stay operator-owned
  environment that Quasar never rewrites.

### 4.9 Homes, templates and volumes

- [F] Managed homes are a host bind at `QUASAR_HOME_ROOT`, mounted at the same path
  (docker-out-of-docker); templates likewise at `QUASAR_TEMPLATE_ROOT`; the XDG runtime dir
  is a fixed bind at `/run/quasar-agent`. Per-host root precedence: admin override → agent
  report → control-plane default. (b §4)
- [F] Named volumes: `quasar-postgres-data`, `quasar-control-tls` (TLS + artwork cache),
  `quasar-agent-data`, `quasar-updater-run`, and on NVIDIA `quasar-nvidia-driver`, whose
  host path the agent learns by inspecting its own container's mounts. (b §4)
- [I] The same-path constraints hold whoever creates the agent container; a new owner must
  reproduce them exactly.

## 5. What RH-01 and RH-05 already give RH-06

- [F] RH-01: a typed runtime facade over the Docker Engine API (Bollard), unix-socket only,
  refusing Docker contexts and TLS endpoints; an owner-token label and name prefixes that
  gate every stop/remove; a boot-only legacy sweep that preserves anything it cannot prove
  it owns. (b §5)
- [F] RH-05: revision + desired/applied digest per setting group; a durable agent journal
  with fsync'd phases and one recovery attempt; boot and connection incarnations
  (`rh05_control_boot`); **owner-scoped admission restrictions** (owner kinds include
  `platform`, `idle_apply`, `recovery`, `legacy`, `reconciliation`); a host-wide operation
  lock. (b §6)
- [F] RH-05 stores **no desired platform-image digests per host and no agent or
  control-plane versions**; the "agent image digest" prerequisite fact was specified but
  deliberately not emitted. (b §6)
- [F] Explicit hand-offs to RH-06: "RH06 owns first-host and additional-host enrollment
  automation, deployment identity, credentials, mount/device provisioning and Quasar
  platform-image replacement" (`docs/rh05/operator-handoff.md:41-43`); "Recovery cannot
  replace a platform image or repair a binary, runtime or mount" (`protocol/agent-api.md`).
  (b §6, c §1)

## 6. Frozen-contract surface

- [F] **Not frozen:** the updater's local socket (`protocol/schema.md` §"Not frozen: the
  updater's local socket"). Replacing *how* the updater executes, behind unchanged
  `release_apply`/`release_state` wire and unchanged tables, needs no amendment. (c §8)
- [I] **Would need an amendment (Opus review + owner sign-off):** a new install/ownership
  mode on `register` and the host body; new eligibility reasons or preflight check ids (the
  lists are closed and include Compose-specific ones); revising the control-plane-target
  apply model toward independent replacement authority; applying components other than
  `control-plane`/`node-agent`; any bootstrap, manager-template or adoption endpoint; new
  tables or columns for service specs, journals or migration state; any change in the
  meaning of a `release_state.state` (`recreating` is defined today as the compose command).
  (c §8)
- [F] Precedent: RH-05 opened with one Tier 3 contract ticket (#334) that blocked every
  implementation ticket; sign-off was recorded per ticket with the `quasar-protocol`
  commit. (c §6)

## 8. Defects and drift found while researching

These are facts about the current code or docs, independent of RH-06's design:

1. [I, code shape verified] Updater has no crash recovery; in-flight state is in memory
   (§4.5). Docs claim otherwise.
2. [F] `.env` and `.env.prev` are rewritten non-atomically (`exec.go:86-95`), while result
   files are atomic.
3. [I] Auto-restore depends on the previous image still being present locally.
4. [F] Stale comments: `redeploy.sh:884-887` and `enroll-host.sh:863-864` say updater
   presence is read once at boot; the agent re-discovers before every `register`.
5. [F] `deploy/.env.example:369-371` still mentions the retired `docker-compose.release.yml`;
   `docs/upgrading.md:219-221` still says "once the apply half ships".
6. [F] The adopt-volumes overlay covers three of five volumes (not `quasar-updater-run`,
   not `quasar-nvidia-driver`).
7. [F] The console has no list or revoke UI for minted enrollment tokens.
8. [F] No result-file retention; no cancel for an in-flight updater apply; updater version
   skew across hosts is not tracked.
9. [F] ADR 0003's `signature_missing` / `signature_invalid` are not yet in `openapi.yaml`.

## 9. Vocabulary already taken

From `CONTEXT.md` (b §8): **Generation** (an app container in a session), **Attempt** (one
target's move to one digest set), **Preflight** (per-target release evaluation),
**Updater**, **Install mode**, **Fleet run** (avoid "deployment", "rollout"), **Legacy
container** (explicitly avoids "adoption"), **Admission restriction**, **Setting source**
("deployment baseline"), **Diagnostic registration**. RH-05 uses *revision*, *incarnation*
and *journal*. Absent: enrollment, node secret, host identity, service owner, external
manager, service spec, adoption of a stack, control-only host, combined host.

## 10. Inferences that shape the product questions

Design consequences, not decisions:

1. Today there is effectively **one owner per stack, and it is Compose plus whoever edits
   `.env`**. Quasar acts through that owner (the updater edits its pin file and runs its CLI)
   rather than owning anything itself. "Transfer ownership once" (#219) therefore means
   moving the desired image record and the replace authority out of the manager's files
   and into Quasar-held state.
2. The durable record of "what should this host run" does not exist in Postgres. The target
   is the latest attempt's `requested_digests`; the truth is the stack's `.env` plus the
   reported commit.
3. The control plane cannot replace itself; today's independent actor is the updater, which
   is itself compose-bound, unauthenticated at its socket, not crash-safe, and updated by
   hand.
4. The restart policy is doing supervisory work (agent `Restart`, NVIDIA provisioning,
   RH-05 restart-scope exits) that any new owner must keep.
5. Host identity and three irreplaceable secrets are addressed by names that a Compose
   project derives (volume names) or stored in a file a manager owns (`.env`). Preserving
   them is the core of any adoption.
6. Session survival bounds control-plane replacement: an outage longer than the agent's
   90 s hold ends sessions even on a non-migrating release.
7. Agent updates stay disruptive until RH-04 lands; RH-06 should not claim otherwise.
8. No automated pre-migration backup exists; whether RH-06 adds one is open.
